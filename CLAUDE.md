# MeetingScribe — Claude Code Guide

## Project Overview

Single-file Python tool: record audio → FunASR transcribe → LLM polish → meeting notes / interview summary / sharing summary.

- **Entry point**: `meetingscribe.py` (everything in one file)
- **Config**: `config.jsonc` (JSONC with `//` comments, sits next to the script)
- **Output dir**: `~/Documents/meetingscribe/recordings/` (created at runtime)

## Project Rules

These are non-negotiable conventions for this codebase. Violations are bugs even if tests pass.

- **All prompts must live in `config.jsonc`.** Every prompt the pipeline sends to any LLM (currently `polish`, `hotwords_extract`, `caption_mt`, `caption_mt_hymt`, `caption_fix_mt`, `caption_fix_mt_strict`, `caption_review`, and `notes_zh` / `notes_en` for each mode) is shipped as an editable block in `config.jsonc`. The `_PROMPT_DEFAULTS` dict in `meetingscribe.py` is **fallback only** — never the sole source. Rationale: prompts are the main lever for tuning product behaviour, and operations / business / non-Python contributors must be able to read and adjust them without touching code. When you add a new mode or a new prompt slot, you MUST:
  1. Add the default to `_PROMPT_DEFAULTS` (so the tool still works if the user deletes `config.jsonc`), AND
  2. Add the exact same prompt as an editable block in `config.jsonc` with a `//` comment explaining what the prompt is for, AND
  3. Verify with `python3 -c "from meetingscribe import load_config, _resolve_prompt, _PROMPT_DEFAULTS; ..."` that `_resolve_prompt` on the fresh config returns text identical to the `_PROMPT_DEFAULTS` entry — i.e. the jsonc override is a faithful copy, not a drifted variant.

## Running the Tool

```bash
python3 meetingscribe.py ui                              # GUI — PyQt6 + Fluent (needs `python3 -m pip install PyQt6 PyQt6-Fluent-Widgets`)
python3 meetingscribe.py record                          # CLI recording (mode defaults to `meeting`)
python3 meetingscribe.py record --mode interview         # interview mode
python3 meetingscribe.py record --mode sharing           # knowledge-sharing / tech-talk mode
python3 meetingscribe.py transcribe foo.wav --mode sharing  # process existing file as a sharing session
python3 meetingscribe.py devices                         # list audio devices
python3 meetingscribe.py config                          # view/edit config
python3 meetingscribe.py captions foo.wav               # replay a recording through the live caption engine (no sound card)
python3 meetingscribe.py hotwords                        # backfill ASR hotwords from existing .polish.txt/.md (--no-llm / --show)
python3 meetingscribe.py hotwords --notion               # one-off import of member/project/term names from Notion (--dry-run / --min-cjk 3)
python3 meetingscribe.py hotwords --show                 # list + show which terms are next to be evicted
python3 meetingscribe.py hotwords --pin 李雷 GKE         # mark terms never-evictable (--unpin to release)
```

Pipeline modes (`--mode`): `meeting` (default, 会议纪要) | `interview` (面试总结) | `sharing` (分享总结, knowledge-sharing / tech talks with audience Q&A). The set of valid modes is exported as `MODES` in `meetingscribe.py` and enforced by argparse.

## Architecture

The pipeline has four steps, each resumable independently:

```
.wav  →  .raw.txt  →  .polish.txt  →  .<mode>.md
        (FunASR)      (LLM polish)       (LLM notes)
```

`<mode>` is one of `meeting` / `interview` / `sharing` (see "Pipeline modes" above). Each mode lives at a distinct suffix (`.meeting.md` / `.interview.md` / `.sharing.md`) so the same recording can carry summaries for multiple modes side by side.

Each step checks whether its output file already exists and skips if so. This means re-running after a crash resumes from where it stopped.

## Key Functions

| Function | Purpose |
|----------|---------|
| `load_config()` | Reads `config.jsonc`, deep-merges with `DEFAULT_CONFIG` |
| `_log(category, message)` | **File-only diagnostic logger** — writes `[HH:MM:SS] [CATEGORY] msg` to the daily log file. Never touches stdout/stderr by default (use `print()` for user-facing output). `--debug` mirrors lines to stderr. Canonical categories: `REC`/`DEVICE`/`AUDIO`/`HOTPLUG`/`RESTORE`/`STREAM`/`MUTE`/`STT`/`POLISH`/`LLM`/`PIPELINE`/`CONFIG`/`MONITOR`/`CAPTION`/`CAL`/`ERR`/`WARN`. |
| `_QuietCapture(category)` | Context manager that redirects stdout+stderr into buffers and forwards captured lines to `_log()`. Wrapped around FunASR `m.generate()` calls to keep tqdm bars out of the console. Captured lines are ANSI-stripped, and tqdm **progress frames are dropped entirely** (`_is_progress_noise` / `_PROGRESS_NOISE_RE`) instead of being logged: tqdm redraws with `\r` and `str.splitlines()` splits on it, so one caption session buried the log under ~5 000 near-identical bar frames out of 8 583 `[CAPTION]` lines (1.3 MB/day). Real diagnostics (warnings, `rtf_avg`, tracebacks) still land in the log — the timings that were being read off the bars are now logged explicitly by the refine / MT workers. |
| `switch_output(name)` | Switches macOS audio output device via CoreAudio ctypes; **no-op on Windows/Linux** |
| `_log_device_plan(msg)` / `_DEVICE_PLAN_LOG_INTERVAL_SEC` | Throttle in front of the `[DEVICE] plan: …` line. `resolve_audio_devices` re-derives the plan on every monitor tick — once a second while recording, from `MultiStreamRecorder._monitor_iteration`'s fallback — and logging each one made it **37 % of a day's log** (measured: 7 385 lines, 6 191 of the gaps exactly 1 s, and only **3 distinct values** all day). A CHANGE is what carries diagnostic value, so a changed message prints immediately and identical repeats collapse to a heartbeat every `_DEVICE_PLAN_LOG_INTERVAL_SEC` (3 s). Replaying the real day: 7 385 → 2 888 lines (−61 %, 37 % → 14 % of the log). The heartbeat can be raised freely — nothing is lost because changes bypass it (10 s → −82 %, 30 s → −88 %). Deliberately lock-free: two monitor threads clearing the check together cost one duplicate line, cheaper than serialising every device resolution. |
| `resolve_audio_devices(query_fresh)` | **Single source of truth** for mic / system-audio source / restore target. Transport-priority (external > built-in; aggregates/virtual rejected for raw picks). Returns an `AudioPlan` dataclass. Called at start, hotplug, and stop. |
| `_restore_output_if_needed(plan)` | Stop-time restore policy: skips `switch_output` when current default is already a physical device (prevents music-app pause). Falls back through the priority list if the plan's target is missing. |
| `_install_device_listeners()` / `_remove_device_listeners()` | macOS-only CoreAudio HAL property listeners on `kAudioHardwarePropertyDevices` + `…DefaultSystemOutputDevice`. Set the module-level `_hotplug_event` so the recorder reacts within ~100 ms. |
| `AudioDeviceMonitor` | Event-driven daemon thread, started by `cmd_ui` and `cmd_record`. Blocks on `_hotplug_event.wait(timeout=_AUDIO_MONITOR_SAFETY_TIMEOUT_SEC)` (30 s) — no fixed-period polling. Runs one synchronous initial tick on `start()` so the process always syncs to the current best device on launch. **Idle branch** (when `_recording_active` is clear): calls `resolve_audio_devices(query_fresh=True)`; runs `_restore_output_if_needed` on the first tick and on every change to the resolved `(restore_output_name, mic_name, sys_source_name)` triple. **Recording branch**: never switches dOut (would pause music apps) and never refreshes PortAudio (would terminate live streams); but DOES call `resolve_audio_devices(query_fresh=False)` + `_reconcile_recording_mutes(plan)` when `(multi_output_name, restore_output_name)` changes, so the Multi-Output's inactive physical sub-devices stay silenced mid-recording on hotplug. The recorder's own `_monitor` thread remains the authoritative reconciler for input streams. Replaces the older GUI-only `_idle_dout_watchdog`. |
| `MultiStreamRecorder` | N simultaneous `sounddevice.InputStream`s; `_monitor` thread (tracked as `self._monitor_thread`) waits on `_hotplug_event` (or 1 s fallback) and on each wake calls `_monitor_iteration()` which: (1) queries the live PortAudio input device set, (2) re-derives `self.wanted` from `resolve_audio_devices(query_fresh=False)` so mic/system-source swaps mid-recording are honoured (USB headset plugged in → `_close_one` built-in mic, `_try_open` USB mic, pre-swap frames are prepended into the new device's frame list to preserve audio continuity), (3) opens newly-appearing wanted devices and closes disappeared / no-longer-wanted ones. `start()` sets the module-level `_recording_active`; `stop()` clears it in a `finally`. `stop()` **joins** `self._monitor_thread` (2 s timeout) BEFORE clearing `self._streams`, eliminating the race where `_monitor_iteration`'s `_try_open` could reset `self._frames` mid-stop and discard captured audio. `_try_open` defensively re-checks `self.recording` inside its lock and discards orphan opens with `[STREAM] discarded post-stop open of device=…`. **Stale streams are detected from CoreAudio, not PortAudio** (`_stale_streams`, first thing in every `_monitor_iteration`): each stream records the device's AudioObjectID when it opens (`_ca_ids`, via `_coreaudio_device_ids`, ~3 ms, safe while streams are open), and a device missing from the live CoreAudio list or present under a NEW id triggers `_rebuild_streams` — close every stream, `_refresh_portaudio()`, re-resolve, reopen, carrying recorded frames per ROLE (so a same-name reopen doesn't lose earlier audio to `_try_open`'s reset, and a headset→built-in mic swap stays one channel; all roles take the same gap, so channels stay aligned). An empty CoreAudio answer never triggers a rebuild. Why: the PortAudio cache is never refreshed mid-recording, so an unplugged device stays "available" and its stream does NOT die — on 2026-10-29 19:03 the headphones were pulled and the `External Microphone` stream ran on for 15 min carrying a **sample-for-sample copy of BlackHole**, so English played aloud in the room produced no captions and no mic audio in the WAV; replugging didn't help because the device comes back with a new id (175 → 190 → 146 the same day) that the stale cache can't reach. Emits `mic-not-opened` / `system-audio-not-opened` warnings via `on_warning` and the `[WARN]` log category — warnings are log-only by design; no sidecar `.warnings.txt` is written. |
| `LiveCaptionEngine` | Live bilingual captions during recording (GUI only, fully local). `feed()` and `MultiStreamRecorder.save()` **downmix all of a device's channels** (mean) rather than keeping channel 0: the old behaviour silently discarded content, which is why replaying a role-separated stereo recording through BlackHole produced garbage captions — the speech sat on channel 1, the digital copy read as RMS 0.0000, and the captions actually came from the microphone re-recording the loudspeakers through the air. The same loss would hit a hard-right-panned participant in a live call. Lifecycle `start()` → `feed(role, frames, sr)` from `MultiStreamRecorder.on_audio_chunk` → `stop()`. Three worker threads: ASR (drains per-source ring buffers every 250 ms, mixes to 16 kHz mono, feeds the streaming backend), MT (preloads its model at engine start; translates finalized segments off a queue, and on idle ticks opportunistically translates the in-flight partial — `partial_translation` events, ≥6-char gate), and refine (`live_captions.refine`): re-decodes each finalized segment's audio with the offline FunASR stack in the background, emits `refined` to replace the caption line and re-queues its translation. **English-dominant segments skip the refine pass entirely** (`_caption_is_english`): it re-decodes with `paraformer-zh`, a CHINESE model, so on English it does not correct but corrupt — a real session (2026-08-26 15:15) logged `changed=True` on 53 of 56 English segments at 1.7–2.5 s each, which is exactly the "refine does nothing useful" the user reported. A re-decode measures ~1.0–1.4 s on M2 (2.5 s on long segments), so `_finalize_segment` also **drops** segments once the refine queue holds `refine_max_backlog` (default 3) — an unbounded queue delivered corrections minutes after the line scrolled away. Every pass logs `[CAPTION] refine seg=… took=…s chars=A→B changed=…` and every drop logs `refine skipped seg=… (backlog=…)`, so a session's `changed=True` ratio tells you whether the pass earns its cost. Events surface via `on_event(dict)` — `status` / `error` / `partial` / `partial_translation` / `final` (carries `role`) / `refined` / `translation` — emitted from worker threads; the GUI re-emits them through `_RecorderState.caption_event` (queued Qt signal). **Sentence breaking is configurable** (`live_captions.endpoint` → `_caption_endpoint_rules`, forwarded to sherpa): `rule2_min_trailing_silence` is the main knob — how much trailing silence ends a line once text has been decoded. It was hardcoded at 0.8 s, i.e. MORE aggressive than sherpa's own 1.2 s default, so a continuous speaker got cut into more, shorter lines than stock. **1.2 is now the default, chosen by measurement** on one 4-minute passage of continuous single-speaker speech (0.8 → 18 lines / 75.8 chars mean; 1.2 → 14 / 97.6; 1.6 → 14 / 95.4). 0.8 → 1.2 is 22 % fewer lines and 29 % longer ones with total characters 1365 vs 1366 — the same content cut differently, nothing lost — and 1.2 → 1.6 does not change the line count at all, so it has plateaued and raising it further buys nothing. Fewer lines is the win that matters downstream, since a review call costs 41.6 s fixed against only 3.4 s per line. Longer lines carry more context into the refine and review passes (both correct better) and cost fewer LLM rows per minute, at the price of the line appearing later. `rule1` applies before any text is decoded, `rule3_min_utterance_length` caps how long one line may grow. Values are clamped to `_CAPTION_ENDPOINT_BOUNDS` and logged, so a junk config value can't silently disable sentence breaking, and they are part of the ASR cache key, because they are baked into the recognizer at construction — without that an A/B in one process would reuse the first set. A/B with `captions <wav> --rule2 …`, which reports lines/minute, mean line length and resulting review batches. **The streaming model is picked by `live_captions.language`** (`_caption_language` → `_caption_asr_model_url`; junk values fall back to `en`, logged). `"en"` (the default) loads **NVIDIA Nemotron Speech Streaming EN 0.6B** (sherpa-onnx int8 export, ~440 MB auto-download); its chunk size is baked into the ONNX graph, so `en_chunk_ms` snaps to the nearest exported variant in `_SHERPA_NEMOTRON_URLS` (80 / 160 / 560 / 1120 ms, NVIDIA WER 8.43 / 7.67 / 7.07 / 6.93 %; default 560). `"zh"` keeps the bilingual zipformer below. An explicit `asr_model_dir` overrides both. The model URL is part of the ASR cache key, otherwise switching `language` between sessions would silently reuse the first recognizer. Why the switch, measured with `captions <wav> --language en|zh` over the same 5-minute English support call: Nemotron produced 28 lines with real casing and punctuation against the zipformer's 21 (which emits ALL CAPS that `_caption_fix_case` has to repair), at RTF 0.178 against 0.097 — slower, still >5× realtime on M2. Two consequences of `en`: (1) **refine is OFF for the whole session** (`_refine_enabled` requires `language == "zh"`) — the per-line `_caption_is_english` gate was not enough, because short English interjections don't sniff as English and the Chinese re-decoder turned `Yeah` into 「需要。」 on that replay; (2) Nemotron ships no `bpe.vocab`, so **sherpa hotword biasing is skipped** (logged) and terminology is left to the MT glossary and the review pass. `captions` reports the model name and the decoder RTF so a language/chunk A/B is one command each. For `zh`: sherpa-onnx streaming zipformer zh-en (auto-downloaded tarball via `_ensure_sherpa_model`, ~320 ms) + opus-mt Marian, with finalized lines re-decoded by the batch pipeline's cached `paraformer-large`+vad+punc stack (`refine`). The former **accurate mode** (`_FunASRCaptionASR`: `paraformer-zh-streaming` partials + energy endpoint → offline 2pass, paired with NLLB) is DELETED along with `live_captions.mode` and the `fast` / `accurate` config nesting: its streaming model is Chinese-only and measurably worse on the English meetings this is used for, and having two ASR paths doubled the surface every caption fix had to be applied to. NLLB survives as an explicit `mt_provider: "nllb"` choice reading its own `live_captions.nllb` block, since it measurably beats opus-mt on some domain terminology. MT provider is switchable via `live_captions.mt_provider`: `"qwen"` (the `DEFAULT_CONFIG` value; **the shipped `config.jsonc` sets `"hymt"`**, see below — flip it to `"qwen"` to exercise the correction path) loads `_QwenCaptionMT` — a local Qwen 1.5B instruct GGUF via llama.cpp (`_ensure_qwen_gguf` auto-download, prompt from `_resolve_prompt(cfg, "caption_mt")`), which injects any `stt.funasr.hotword` terms found in the source line as a keep-verbatim glossary; on ANY load failure (llama-cpp-python missing, model missing) it logs and falls back to opus-mt Marian. Cached qwen backends get `set_hotword()` refreshed on reuse. **Finalized lines** additionally go through `correct_and_translate` (`qwen.correct`, default on): ONE combined call that first repairs obvious ASR errors (homophones / broken English words like `lang 三姆斯`→`LangSmith`) using the last 3 finalized lines as rolling context (`_mt_context`) + a **line-scoped** glossary, then translates. `_glossary_candidates(text, hotwords, limit)` picks that glossary: literal (case-insensitive) hits first, then fuzzy near-misses — a hotword qualifies only if it shares a ≥3-character run with one of the line's alnum / CJK-flanked-alnum spans (≥3 chars) AND scores SequenceMatcher ≥ 0.45, and spans already covered by a literal hit are excluded from fuzzy matching. Capped at `qwen.glossary_max` (12). Rationale, all measured against the real 100-term table: dumping the whole table was the main driver of the model applying unrelated terms; ratio alone let `dora` pull in `RMA`/`Portland`; without the literal-coverage rule `用 LangGraph` also dragged in LangSmith/LangChain/LangFuse. Pure-CJK terms are literal-match only — `里雷`→`李雷` would need pinyin, which is not a dependency here. The MT worker emits the corrected line as a `refined` event before the `translation`. `_parse_fix_mt` guards against small-model failure modes: missing 翻译： line → whole reply used as plain translation; corrected line outside 0.66x–2.0x of the original length OR SequenceMatcher similarity < 0.5 → discarded (catches dropped clauses and translation-in-修正-line; a bare prefix scores HIGH on similarity, which is why the length bound exists). **Output shape is pinned by a GBNF grammar** (`qwen.grammar`, default on): `_FIX_MT_GRAMMAR` forces `修正：<≤400 chars>\n翻译：<≤400 chars>`, which structurally kills example leakage and repetition loops. Grammar on → the **zero-shot** prompt `caption_fix_mt_strict` is used; grammar unavailable (older llama-cpp-python without `{m,n}` bounded repetition → `LlamaGrammar.from_string` raises, logged under `[CAPTION]`) or `grammar: false` → the **few-shot** `caption_fix_mt`. Both prompts must stay rule-identical; only the format example differs. The few-shot example exists because abstract format rules alone made the 1.5B model leak translations into the 修正 line — do not delete it, and do not delete the strict variant either: a 1.5B model copies example wording into its own output, which is why the example goes away once the decoder enforces the format. Measured on M2 Metal (q4_K_M, min of 3): grammar costs **1.22 s → 1.80 s** per finalized line, while prompt length is noise (few-shot 1.15 s vs zero-shot 1.22 s). The plain `translate()` path is deliberately **not** grammar-constrained — it also serves in-flight partials (+0.30 s there, 0.42 → 0.72 s) and has no structure to enforce. **Do not switch an English-source meeting to qwen**: measured on 4 real English caption lines, the 1.5B model returned the corrected ENGLISH as its 翻译 line in 3 of 4 — it corrects well but does not reliably translate en→zh at this size, while Marian at least always produces Chinese. `mt_provider` accepts `"marian"` (default, aliases `opus` / `opus-mt`) / `"nllb"`, cached under `("mt", want)` so both can coexist. **`"hymt"` (alias `hy-mt`; the shipped `config.jsonc` value) loads `_HYMTCaptionMT`** — Tencent HY-MT1.5-1.8B Q4_K_M GGUF via llama.cpp (`live_captions.hymt` block, `_ensure_qwen_gguf(..., label="hymt")` auto-download from `tencent/HY-MT1.5-1.8B-GGUF`, ~1.1 GB; license excludes the EU/UK/KR), falling back to Marian on any load failure. It is a dedicated translation model, which is what English meetings were missing: Qwen 1.5B returns English as its translation, and opus-mt **truncates long lines** — measured on one 5-minute English support call replayed with `captions <wav> --language en --mt marian|hymt`, opus-mt lost the second half of 9 of 25 translations (Marian's own length cap on ~170-char Nemotron lines) where HY-MT translated all of them in full and fluently, at 1.14 s/line against 0.94 s (max ~2.5 s). Translate-only: it has no `correct_and_translate`, so the MT worker takes the plain path. Prompt `caption_mt_hymt` is the model card's own ZH<=>XX template (`{glossary}` / `{dst_lang}` / `{text}`) — keep edits minimal, it is trained on that wording; decoding is greedy with the card's `repeat_penalty` 1.05 (not its temperature 0.7: a partial and its final must not translate differently). Hotwords go in through the card's terminology block (`X 翻译成 X`) with two filters, both found on that replay: matching is word-boundary (`_hotword_hits`), since substring matching let `CU` hit "customer"; and on an English line only `_hymt_strong_term`s (CJK / digit / inner capital: `GKE`, `BigQuery`, `K8s`) are pinned — the list is mined from Chinese meetings and carries ~176 plain English words (`support` / `release` / `scope`), which pinned verbatim produced 「有很多 engineering 方面的内容需要被 release」. `_close_caption_llm_backends` (atexit) closes cached llama.cpp models: otherwise ggml's Metal device is freed by a C++ static destructor while the model still holds its residency set and the process aborts with exit 134 after the work is done. `captions --mt` overrides `mt_provider` and the report prints the MT backend and mean seconds per finalized line (`engine.mt_final_secs` / `mt_final_count`). **Sentence-level translation** (`live_captions.mt_sentence_split`, default on; marian / nllb / hymt only — qwen's correction path needs the whole line): `LiveCaptionEngine._translate_units` splits a line with `_split_caption_sentences` (`.!?` + whitespace, or `。！？`; pieces under `_CAPTION_SENT_MIN_CHARS` weighted by `_caption_unit_weight`, CJK counting double, ride along with the next one and are never merged back, since a unit's text is its cache key) and caches each FINISHED sentence (`_mt_unit_cache`, 400 entries), so a partial refresh pays only for its unfinished tail and the final reuses what partials already translated. The measured gain was small, and the reason matters: on the conversational English support call Nemotron emits little sentence punctuation ("…answer these questions So that's a that's a kind of the way…"), so most lines are ONE unit — 6 cache hits in 5 minutes, P90 final→translation 3.04 → 2.59 s, median unchanged (1.12 s). Kept on because it is harmless and splits well-punctuated speech, and because short calls are what keep opus-mt from truncating. **Contextual translation** (`hymt.context_lines`, prompt `caption_mt_hymt_context` = the model card's contextual template, built in one regex pass so caption text containing `{text}` can't expand a placeholder) exists but is OFF: measured with 2 lines of context, the 1.8B model translated the context as well — one line's translation came back carrying the previous line's Jira decision — and it was slower (median 1.12 → 1.53 s, partial translations 207 → 160). `captions` reports `定稿→译文` (median / P90 / max wait from a line's final event to its first translation, from timestamps the replay stamps on its trace) and the unit call / cache-hit counts. Every llama.cpp call holds the backend's `_llm_lock`; the atexit close waits up to 10 s for it and then keeps it held, because freeing a model under a running decode aborts with a second ggml assertion (`backend_res != nullptr`) — seen when the engine's stop abandoned a slow MT worker mid-call. On domain terminology the two trade wins (measured): NLLB kept `PoC` and `包裹` where opus-mt produced 「钻石交易市场」and 「土地」, opus-mt kept `RFP` where NLLB dropped a letter; NLLB costs 760–1200 ms/line against 120–150 ms. `_glossary_candidates` skips FUZZY matching on English-dominant lines (literal hits only): English words share 3-character runs with unrelated hotwords constantly — `"…were told about this RFP around four day"` matched `Acme` via `were`/`ere`, and one line pulled in eight terms. Heavy backends are cached in module-level `_caption_backend_cache` across recording sessions (`reset_session()` rebinds callbacks + clears per-session state). Finalized/refined text **and the in-flight partial** both pass through `_caption_tidy_zh` (drops pure fillers 嗯/呃/哎呀/唉 per `_CAPTION_FILLERS` — grammatical particles 呢/啊/吧 stay; collapses stutter n-gram repeats 「所以就像所以就像」→「所以就像」; sweeps orphan punctuation) so the translation input is clean too. **Chunk-boundary dedup** (`_append_hypothesis`) attacks the same duplication at its source. Streaming decoders are append-only — once a token is emitted it is never revised — so a syllable split across a chunk boundary gets committed twice. Measured on 18 s of real audio: the streaming pass produced 129 chars where the offline pass produced 101 (+28 %), i.e. the speaker did not say 28 of those characters. Since the duplicate sits at the JOIN, `_SherpaCaptionASR._advance_hypothesis` keeps the recognizer's raw hypothesis (`_raw_hyp`) separate from our deduped one (`_clean_hyp`), isolates each chunk's delta, and runs it through `_dedup_caption_boundary`; a recognizer that rewrites earlier text (a rescoring build, not the append-only behaviour measured here) is trusted wholesale rather than splicing two disagreeing histories. Measured result on the same slice: 129 → 124, and 115 after the collapse layer, against the 101 offline baseline. The 2-character minimum overlap stays: relaxing it to 1 bought exactly ONE more character while risking a genuine 「看看」 split at the join, because the remaining repeats (做做 / 动动 / 成成) are INTRA-chunk — emitted inside a single delta, where boundary logic structurally cannot see them — and homophone substitutions (在→再) are not textual duplicates at all. Tidying the PARTIAL matters as much as the final: a streaming decoder oscillates between hypotheses while a sentence is still open, and measured on one real meeting the partial line carried 4-19x the duplication of the offline transcript of the SAME audio (single-char repeats 85 vs 21 per 1000 chars, triples 25 vs 1.3, 2-char word repeats 55 vs 5.4) — 「大大大家大家」/「在在在在」/「训练练练习」 were on screen verbatim because the collapse only ran at finalize. It now runs in `_emit_partial`, which also gives the opportunistic partial translation a clean input. The remaining 2-char single-char repeats (说说 / 高高 / 年年) stay ON PURPOSE — Chinese reduplication is legitimate, so `_CAPTION_STUTTER_2CHAR` only lists characters that never reduplicate; for Chinese finals the refine re-decode brings duplication down to offline levels anyway. English additionally goes through `_caption_fix_case`: the streaming zipformer emits ALL CAPS (`AND THEN OKAY WERE CON YEAH`), which read as shouting next to the mixed-case lines the refine pass produced for the same session. Only fully upper-case text is touched (any lowercase → left alone, so `这个 GKE 集群` keeps its acronym), hotwords get their configured spelling back, and standalone `I` / `I'll` stay capitalized. **Translation output** goes through `_collapse_mt_repeats`: greedy decoding (num_beams=1, chosen for latency) degenerates into loops on noisy ASR input — one real line came back as 「雅 的 内容」×30 then `Ya`×100. ## Provider System

Three independently configurable providers (set in `config.jsonc` or via CLI flags):

- `transcribe_provider`: `funasr` (local, default) | `openai` | `gemini`
- `polish_provider`: `codex_proxy` (default) | `claude` | `openai` | `gemini`
- `meeting_notes_provider`: `codex_proxy` (default) | `claude` | `openai` | `gemini`

`codex_proxy` calls `codex -p proxy exec`; `codex_personal` calls plain `codex exec`; `claude` calls `claude -p <prompt>`. Legacy `codex` config names resolve to `codex_proxy`.

**Fallback chain** (`llm_fallback`, default `["claude"]`): when Codex proxy has exhausted its configured model list or otherwise fails, Claude is tried before the run is given up on. Set it to `[]` to restore fail-on-first-error. Calendar and Notion independently use `calendar.provider_chain`.

## Config System

- **`hotword.jsonc` carries bookkeeping, not just a string.** `_load_hotword_store()` / `_save_hotword_file(hotword, store)` read and write `hotword` (the space-separated list, still the first key and still hand-editable), `pinned`, `hits`, `last_seen` and `epoch`. A flat `{"hotword": "a b c"}` file — everything written before this existed, and anything a human edits — loads as all-rolling with no history, and the flat key is always written, so older builds keep working. A `pinned` entry missing from `hotword` is still added to the list, so pinning a name is a one-line edit rather than two.
- **`hotword.jsonc` is separate and gitignored.** The hotword list is auto-mined from every meeting, so it fills up with colleague names, customer names and internal codenames — local data that must not ship with a public repo. `config.jsonc` keeps `stt.funasr.hotword` as an empty default; `_load_hotword_file()` overrides it at load time when `hotword.jsonc` has content, `_persist_hotwords` writes THERE, and `_migrate_inline_hotword` blanks any legacy inline value in `config.jsonc` on the next extraction so a stale copy can't linger in a tracked file. Only `hotword.jsonc.example` is committed. A broken hotword file is logged and ignored, never fatal — no contextual biasing beats no recording. **Tests must redirect `HOTWORD_FILE`**, not just `CONFIG_FILE`: forgetting to overwrote the developer's real list with two-word fixtures, which is why `tests/test_hotwords.py` has an autouse fixture pinning it into `tmp_path`.
- `config.jsonc` is parsed with `_strip_jsonc_comments()` (regex strips `//` lines)
- `_deep_merge(DEFAULT_CONFIG, on_disk)` — nested dicts merge recursively; on-disk values win
- `load_config()` never auto-writes back; `save_config()` writes plain JSON (comments lost)
- CLI flags override config at runtime but never persist

## GUI (PyQt6 + Fluent)

- Light theme (`setTheme(Theme.LIGHT)`); rounded cards via `_style_as_card(...)` + `_CARD_BG = "#f5f7fa"`. Outer padding comes from `_VIEW_MARGIN_H` (14) / `_VIEW_MARGIN_V` (24) and the recording view's two columns are separated by `_VIEW_COL_GAP` (12). These are named constants rather than per-view literals because the horizontal value had drifted to 28 / 24 / 28 across recording / history / config, which shifted the content sideways when switching tabs in the left nav.
- **Stopping a recording never blocks the Qt thread.** `_RecorderState.stop_recording()` closes the streams synchronously, then runs the caption engine's `stop()` and `MultiStreamRecorder.save()` on a non-daemon `recording-save` thread; status is `saving` (record button disabled) until `saved` fires back on the Qt thread, so the next session can't start while the old ASR thread still owns the cached recognizer, and `closeEvent` joins the thread so a quit can't truncate the WAV. `save()` itself streams in `_SAVE_BLOCK_FRAMES` blocks: the old whole-array version peaked at ~7.5 GB of transient float copies for an 83-minute recording and froze the window for 25 s (log, 2026-10-22 16:47).
- Thread safety: each pipeline runs on its own `QThread` via `_PipelineWorker` (a `QObject`). Signals: `progress(int)`, `log(str)`, `done(str)`, `failed(str)`. Cross-thread UI updates use `QTimer.singleShot(0, ...)`.
- Pipeline run log (`log_view` in the recording view, `h_log_view` in History): shown while a run is in flight, then **cleared and hidden on success or cancel** via `_hide_pipeline_log()`, with the outcome reported as an `InfoBar.success` toast carrying the artifact filename. Every line is already in the daily log file and the action button flipping to "Open …" is the real confirmation, so a pane parked on screen afterwards is just clutter. **Failures keep the log** — it is the only place the failing step is visible without opening the log file.
- Action buttons toggle between "Generate X" (light gray) and "Open X" (accent blue, `#0a84ff`) based on whether the corresponding artifact exists on disk — see `_apply_open_btn_style(btn, is_open)` and `_refresh_action_buttons()` / `_refresh_h_action_buttons()`.
- Internationalisation: `_LANG["current"]` holds `"zh"` / `"en"`; every translatable widget either registers a callback in `self._lang_callbacks` (static labels) or is re-rendered from a dynamic refresher inside `apply_language()` (state-dependent labels). The 中文 / EN toggle (a non-selectable NavigationItemPosition.BOTTOM item under 配置 in the left nav) flips state and calls `apply_language()` on every view.
- `_confirm_dialog(parent, title, msg)` — custom Yes/No `QMessageBox` whose button labels go through `_t("ctx.confirm_yes")` / `_t("ctx.confirm_no")` so the EN toggle actually delivers an all-English UI (Qt's built-in `QMessageBox.question` would otherwise label buttons from the system locale).
- Right-click context menus on both history lists: 重命名 → 删除本次会议所有记录 → 在 Finder 中显示. Delete is gated on `self._pipeline_thread is None` (can't yank files from a running worker). **Menu pattern (do not regress)**: menus are shown with async `menu.popup()` + `WA_DeleteOnClose`, action handlers are deferred via `QTimer.singleShot(0, …)`, and the menu is pinned to `QGuiApplication.screenAt(global_pos)`. A nested `menu.exec()` inside the context-menu event crashed in the Cocoa popup-show path (SIGSEGV in libqcocoa via `QMenu::exec → QWidgetPrivate::show_sys`, see 8/11–8/12 `.ips` reports) and modal dialogs opened mid-teardown left ghost menus stuck on screen. Also: signal wiring belongs in `_wire()` — a past bug had `history_list` connects inside `_render_captions()`, multiplying connections per caption render and stacking hundreds of menus per right-click.
- Live bilingual captions: the recording view splits 2:3 into a LEFT column holding the record-controls card (`recordingCardLeft`) and a RIGHT column fully owned by the caption panel (`recordingCardCaptions`). The meeting-history card that used to sit below the controls is GONE — the left nav already has a 历史 view with the same list, search, context menu and pipeline buttons, and the duplicate was what squeezed this column. **The controls card wraps its content in a transparent `ScrollArea`** (same shape as the history detail pane: card QFrame → ScrollArea → inner QWidget), which is load-bearing: the column is mostly fixed-size content that grows ~200 px once 停止任务 / progress / log_view appear, and when the total exceeded the card height Qt shrank children below their minimums — `setFixedHeight(180)` on `mic_block` included — so the timer painted over the volume row and the hint landed on the mic disc. Verified offscreen at 1100×560: overlapping before, scrolling cleanly after. Horizontal scrolling stays enabled too, because turning it off silently truncated the notes buttons (「生成分享总结」→「生成分享」). Panel header: a single `SwitchButton` (on/off), disabled while `status != "idle"` (caption prefs are session-scoped). There is no mode selector — one recognition path means nothing to choose, and the panel does not name it either. Preference changes persist through `_save_config_preserving_comments` into the `live_captions` block. Rendering: `_caption_rows` (finalized src/dst pairs, each stamped with arrival time `t` and speaker `role`) + `_caption_partial` → `_render_captions()` builds HTML into a `TextBrowser` (source line dark, translation `#0066d6`, partial gray italic); rows are paragraph-merged at display time via `_group_caption_rows`, where **a speaker change is the primary break** — one person's speech flows and wraps as a single block, the shape Google Meet's live captions use — while `merge_gap_ms` (30 000) and `merge_max_chars` (800) are only safety valves (data rows stay 1:1 with engine segments). The old defaults were 2 500 ms and a `max_chars` of 120 that **never reached the call site at all**, so a continuous speaker was chopped up: measured on two real sessions (1121 and 264 finalized lines), only 35 % / 55 % of adjacent lines merged at 2.5 s versus 100 % / 98 % at 30 s. The valves are kept rather than removed because an unbounded paragraph makes every appended line re-render an ever-growing block — the renderer patches per group — and a genuine 30 s pause from the same speaker really is a new thought and joined with `_join_caption_texts` (bare join between CJK, space at ASCII-alnum boundaries); the in-flight (still-being-spoken) line is rendered **inline at the tail of the last paragraph** by `_caption_groups_html` — gray italic after the source text, its partial translation in light blue after the translation line — so speech reads as one continuous flow (user request; it used to sit in a separate `caption_partial_label` box under the pane). The separate widget existed because the partial refreshes ~2×/s per `partial_interval_ms` (~70 % of all caption events) and each one used to re-lay-out the whole pane; with `_CaptionDocRenderer` below that is a single tail-group patch (0.4 ms), routed through the same debounced `_schedule_caption_render`. Spacing between the settled text and the partial is decided on the raw text (`_join_caption_texts`), never on the markup. Attribution is provisional — the speaker is only known at finalize, so a partial sits on the last paragraph and moves under its own tag if the speaker changed. A `status: stopped` event clears any partial the flush never finalized. **Document updates go through `_CaptionDocRenderer`** (module-level, so it is testable against a real `QTextBrowser`): it keeps the HTML of every committed group, diffs the new list, and patches only from the first divergence with a `QTextCursor` instead of calling `setHtml`. Bookkeeping is by BLOCK NUMBER — each group is exactly `_BLOCKS_PER_GROUP` (2) paragraphs, so group *i* starts at block *2i* and `blockCount == 2 × len(committed)` is checked before every patch; a violation, a divergence with no untouched leading group (`k_eff < 1`), or an invalid block falls back to a full `setHtml`, so a bookkeeping bug can only cost performance, never a corrupted pane. Appends deliberately rewrite from the LAST committed group rather than inserting at the document end: block `2k` does not exist yet when appending, and `insertHtml` at the end merges inline into the previous block (verified — it produced 3 blocks where 4 were expected). Measured with real Qt: on a 12 000-group document an append costs **0.5 ms** and a tail edit **0.4 ms**, against **140 ms** for `setHtml`. Simulating whole 4-hour sessions end-to-end (rows → prune → group → render, two renders per line): full rebuilds are 0.2–0.8 % of renders at 15/30/66 lines-per-minute, average render 0.15–0.23 ms. The view follows the tail only when the user is already scrolled to the bottom (≤8 px margin) so scrolling back during a session works. **Retention is by TIME**: `_prune_caption_rows` drops rows older than `live_captions.history_minutes` (default 180 = 3 h of scroll-back), with `history_max` (12 000) as a pure memory backstop — a row cap alone can't promise a duration, since 3 h is 2 700 rows at 15 lines/min but 11 887 at 66. Eviction is BATCHED (`slack_secs=60` / `slack_rows=200`) and that is load-bearing, not a micro-optimization: dropping one row per append shifts every paragraph, so group 0 changes and the renderer can no longer patch — the pane would re-layout in full on every line once the window fills. Batching turns that into ~1 rebuild/minute (the measured 0.2–0.8 %). The window is therefore a *minimum*; up to the slack of extra history may be retained. Engine events arrive on the Qt thread via `state.caption_event` → `_on_caption_event`, **through a per-session gate**. `_RecorderState` bumps `_caption_session` on every `start_recording` and hands the engine a closure that drops events whose captured token is no longer current. Load-bearing for stop-then-immediately-start: `stop()` cannot interrupt an in-flight worker call, and the log shows the review worker emitting 6 rewrites **23 s after** `engine stopped` (2026-08-27 16:21:33). Segment ids restart at 1 every session and `_on_caption_event` matches `refined` / `translation` / `speaker` by id ALONE, so a late correction lands on the NEW session's row with that id — and the review buffer pops oldest-first while running a batch behind, so the ids in flight at stop time are precisely the early ones the next session immediately produces. The token is compared rather than the engine's running flag, so the session being stopped still delivers its ASR-flush tail. `stop()` itself is budgeted per role (`_CAPTION_STOP_ASR_TIMEOUT` 5 s, `_CAPTION_STOP_TOKEN_TIMEOUT` 0.5 s for the rest): five threads at a flat 5 s could block the Qt thread for 25 s on every stop. The ASR thread keeps the real budget because it shares the cached streaming recognizer with the next session, and interleaving two sessions' audio into one decoder stream corrupts recognition rather than merely delaying it; the others are abandoned after a token wait and logged, since their late events are now harmless. `_start_recording` clears the pane and pushes the switch into `_RecorderState.captions_enabled`; `_RecorderState` owns the `LiveCaptionEngine` lifecycle around the recorder.
- Calendar chip (recording view): a single row between the subtitle and the mic disc showing the linked event (`📅 <title>  HH:MM–HH:MM ▾`) with a sub-line of `N 人 · 会议室 · 🔗 Notion`. Placed *above* the record button because it must be read before recording starts — the choice names the file at creation time. Clicking opens a picker of today's events (plus 手动命名 / 不关联 / 重新读取) built with the same async `QMenu.popup()` + `WA_DeleteOnClose` + deferred-handler pattern the history menus use. **Always present, including when `calendar.enabled` is false** — the off state is a muted dashed row (`📅 日程关联已关闭`) that routes to the config card on click. For the same reason the loaded-but-unlinked state says `📅 选择日程（今天 N 个）▾` rather than a bare 未关联 — 未关联 sitting next to four pickable events reads as a failed sync — and `📅 今天没有日程` is a separate string for the genuinely-empty case. Disabled (not hidden) while `status != "idle"`: the file is named, so offering to re-link it would be a lie. A chip in the error state routes to the config card via `MainWindow.switch_to_config()` rather than opening an empty picker. **Background loads cross back on a `pyqtSignal`** (`RecordingInterface.cal_loaded`, `ConfigInterface.cal_checked`), not `QTimer.singleShot` — a timer started on a plain worker thread has no event dispatcher there and is never delivered (Qt logs `current thread's event dispatcher has already been destroyed`), so the fetch succeeds in the log and the UI silently never updates. That was a real bug during development; the pre-existing `singleShot(0, …)` calls in this file are all *on* the Qt thread, deferring menu handlers.
- Calendar config card: `启用日程关联` toggle + one status row per service + 重新检测 + a 打开 claude.ai 连接器 button shown only for the two states it can actually fix (`connector_missing` / `needs_auth`). **The toggle IS the preflight**: flipping it on runs the check and only commits if the required connector answers, otherwise the switch bounces back and an `InfoBar.warning` names the fix — so a broken setup surfaces while the user is deliberately enabling the feature, not one minute before a meeting. `_load_into_widgets` sets the switch with `blockSignals`, or a plain reload would be treated as the user enabling it and would fire a 25 s sweep.
- Markdown callouts: the meeting-mode notes prompts instruct the LLM to emit GitHub/Obsidian-style callout blockquotes (`> [!important]` decisions, `> [!tip]` action items, `> [!warning]` risks). Qt's `setMarkdown` renders these as plain quotes with the literal `[!type]` text, so every notes render in `HistoryInterface` goes through `_set_body_markdown(md)` → `setMarkdown` + `_apply_callout_styles(doc)`. The post-pass finds blockquote blocks via the `BlockQuoteLevel` block property, paints each callout run with a colored card background, and replaces the literal marker with a bold colored icon+title (a `U+2028` line separator keeps the body on its own line — Qt merges `> [!type]\n> body` into a single paragraph via soft line break). Type→style map is `_CALLOUT_STYLES` (note / tip / todo / important / warning / caution; unknown types get a gray 💬 fallback). Plain blockquotes without a marker are left untouched. Raw/polish text views (`setPlainText`) are unaffected.

## Platform Notes

- **macOS**: Full support. `switch_output()` uses CoreAudio ctypes to auto-switch audio devices around recording.
- **Windows**: `switch_output()` is a no-op. User sets up VoiceMeeter Banana + VB-Audio Virtual Cable manually. Use `os.startfile()` to open result files.
- **Linux**: Untested. `switch_output()` is a no-op. `xdg-open` used for result files.

### macOS music-pause behavior on recording

Recording system audio requires routing playback through the Multi-Output Device (which tees to BlackHole for capture). The recording start/stop paths therefore change `kAudioHardwarePropertyDefaultOutputDevice` (`dOut`) twice per session: physical → Multi-Output at start, Multi-Output → physical at stop. macOS delivers a default-output-changed event on every `dOut` write, and many audio apps (Apple Music, Spotify, Safari, Chrome) react by pausing playback.

To make this workflow music-pause-free, the start path is **conditional**: if the user's permanent `dOut` is already the Multi-Output Device, the start-time switch is skipped. The `_recording_did_switch` event tracks whether the start path actually performed a switch; `_restore_output_if_needed(plan, reason="post-recording")` only runs when the event is set. Idle-state callers (`AudioDeviceMonitor`) bypass the gate via `reason="idle-event"` so hotplug-driven `dOut`+`sOut` alignment still works.

**Lifecycle ordering** (important for maintainers): `_recording_did_switch` is cleared at the **entry of the recording-start lifecycle** in both `cmd_record` and `cmd_ui` — BEFORE the start-time `switch_output` decision. The start path sets the flag only when `switch_output(multi_output_name)` actually runs. `MultiStreamRecorder.start()` does NOT touch the flag (clearing it there would wipe the bit set moments before by the start-path switch).

**Recommended user setup for zero music pauses:**
1. In *Audio MIDI Setup*, configure the Multi-Output Device to contain only `[BlackHole 2ch, your preferred physical output]` (e.g. BlackHole + External Headphones). Including multiple physical outputs causes audio to play through all of them simultaneously.
2. Right-click the Multi-Output Device in Audio MIDI Setup and set it as the macOS default output.
3. Now MeetingScribe's start/stop are silent — `_recording_did_switch` stays clear and music apps see no device change.

**Known limitation**: when the permanent `dOut` is a physical device (the default macOS setup most users have), bugs 1 and 3 of the music-pause report are intrinsic to the dOut-switching strategy and cannot be eliminated without a different recording stack (a dynamic session-scoped aggregate, rejected in `robust-audio-device-handling`; or `SCStream` screen-capture-with-audio, out of scope).

### Apps that bypass the Multi-Output (`_BypassMonitor`)

Some apps don't follow the default output into the Multi-Output Device. Observed with 轻听英语 (`cn.com.langeasy.ZdcQlisten`): when recording switched dOut from the headphones to 多输出设备, the app landed on the aggregate's clock-master sub-device — BlackHole — so captions and the WAV were fine while the user heard nothing. Every device-level state looked healthy (headphones unmuted at 37 %, an active sub-device of the aggregate at 48 kHz); the tell was that **the aggregate itself was not running** while BlackHole was, and the per-process query put the app on `['BlackHole 2ch']` alone. Why the app picks the clock master is inferred (iPad-style apps typically don't support aggregate devices), not verified.

- `_audio_output_processes()` reads macOS 14.2's per-process audio objects (`prs#` → `piro` running-output, `ppid`, `pbid`, `pdv#`); None when unavailable.
- `_bypassing_processes(procs, capture, transports, own_pid)`: a process is bypassing when it outputs to the capture device and to NO physical device. Measured distinction: a player going through the Multi-Output lists BlackHole **plus** the physical sub-device (`['BlackHole 2ch', 'MacBook Air Speakers']`); the bypasser lists BlackHole alone. Our own pid is excluded (our capture stream shows up in our device list too).
- `_BypassMonitor` (thread, one per recording, `_start_bypass_monitor` / `_stop_bypass_monitor` in both `_cmd_record_body` and `_RecorderState`) runs its first check **synchronously at the press of record**, then **on CoreAudio events, not a timer**: `_ProcessAudioListener` listens on the system object for `prs#` (an app starts/stops using audio), `dev#` and `sOut` (the forwarding target changes), and on every process object for `pdv#` / `piro` (an app's output devices) — new process objects are picked up by `sync()` after each `prs#` event. The app re-routes a few hundred ms AFTER the default-output switch, which is exactly a `pdv#` event. Callbacks only set an Event; checks run on the monitor thread after a `_PASSTHRU_DEBOUNCE_SEC` (150 ms) coalescing wait, since one switch fires 2-4 callbacks within 100 ms. The only timed wakeups are `_PASSTHRU_SAFETY_TIMEOUT_SEC` (30 s self-heal, the AudioDeviceMonitor pattern) and the idle grace. It was a 1 s poll first; measured with real listeners on a process moving Multi-Output → BlackHole → exit, forwarding started 0.2 s after the switch and every one of the 8 checks in 13 s matched a real event. While a bypasser exists, `_BlackHolePassthrough` plays BlackHole (its own 2-ch input stream, independent of the recorder's mono stream and of captions) to the current physical output (`_get_system_output_device`, follows a headphone plug; never a virtual/aggregate device, so no feedback loop), through **one PortAudio full-duplex stream** (`sd.Stream(device=(BlackHole, output))`, callback `outdata[:] = indata`; status flags counted and logged at stop as `stream stats … glitches=`). The two devices run on independent clocks and BlackHole delivers input in ~85 ms bursts (its 4096-frame IO buffer), so SOMETHING must buffer between them; PortAudio's CoreAudio backend does it here. History, so it isn't re-derived: the first version had no buffer and starved 51 times in 5 s (measured) — the user heard noise drowning the speech; a hand-written jitter buffer then fixed it at 0.12–0.17 s delay (prefill had to exceed one 85 ms burst — 40 and 60 ms both troughed at zero), but was ~60 lines of our own, and the user preferred the simpler duplex stream at the cost of delay. Duplex measured 0 under/overflows in 20 s with the recorder's own BlackHole stream open; it reports ~0.6 s latency (0.43 in + 0.17 out, PortAudio's own figure) and cannot go lower — `latency="low"` fails to start (AUHAL -10863), `latency=0.1` is ignored. Acceptable because forwarding only serves the rare bypassing app, used for listening; the visible cost is pause taking ~0.6 s to go quiet. **The stream runs in a child process** (`_PASSTHRU_CHILD`, spawned with `sys.executable -c`, prints `ready`, forwards until its stdin closes, prints its glitch count): the callback is Python, and in-process it competed for the GIL with the caption engine's threads — a real 7-minute session logged `glitches=2` that the user heard as dropouts and jumps, and with 4 busy Python threads alongside, in-process forwarding measured 157 under/overflows (146 sine discontinuities) in 40 s against **0** in a subprocess under the same load. Stdin-EOF as the stop signal also means a MeetingScribe crash can't orphan it (verified: SIGKILL the parent → child gone). `_BlackHolePassthrough.pid` is excluded from the double-playback warning, since the child itself lists BlackHole among its devices. Diagnostics that settled the earlier noise reports, so they aren't repeated: the BlackHole capture chain itself is clean (sine written + read back, 3 × 20 s, 0 discontinuities); 轻听英语's own audio in bypass mode does contain occasional dropouts (0.9–5/min, also in the WAV — not fixable here), and none when it goes through the Multi-Output. Before any test that writes into BlackHole, check the user isn't recording — the bypass monitor will forward the test signal into their headphones (it did once). It stops once no app has bypassed for `_PASSTHRU_IDLE_GRACE_SEC` (3 s) — riding out a pause or a track change — and at recording stop, which also removes the listeners.
- Known trade-off: BlackHole also carries apps that DID go through the Multi-Output, so while forwarding is on they are heard twice (logged once per recording).
- Config `audio.passthrough_bypass` (default true). Log tag `[PASSTHRU]`. Verified end-to-end with a process playing into BlackHole: forwarding started 0.12 s after `start()` (start-time check) and stopped ~3 s after the player exited.
- `_BypassMonitor` must not define `_target`: `threading.Thread` keeps its run-callable there and sets it to None (it did, and every tick raised `TypeError`).

### macOS per-device mute lifecycle (Multi-Output sub-devices)

When the user's Multi-Output Device fans out to BOTH speakers AND headphones simultaneously (sub-list includes `BuiltInSpeakerDevice` + `BuiltInHeadphoneOutputDevice`), plugging in headphones during a recording causes audio to play from both at once. The fix is to mute the inactive physical sub-device(s) for the duration of the recording — leaving `dOut` unchanged (no music pause) while BlackHole capture continues uninterrupted.

**Helpers** (`meetingscribe.py`):

- `_ca_get_device_mute(name)` / `_ca_set_device_mute(name, muted)` — CoreAudio `kAudioDevicePropertyMute` accessors, output scope, master element. macOS only.
- `_get_multi_output_physical_subs(name)` — reads the Multi-Output's `kAudioAggregateDevicePropertyComposition` CFDictionary (we use `acom`, not `agdv` — the latter returns `kAudioHardwareUnknownPropertyError` on at least some macOS versions), extracts each sub-device's UID, looks up the matching device name, filters out virtual / aggregate transports.
- `_reconcile_recording_mutes(plan)` — for each physical sub of `plan.multi_output_name`, ensures `desired = (sub != plan.restore_output_name)` matches the device's current mute state. Wires the lifecycle through `_active_mutes: dict[name, original_bool]` so `_restore_all_recording_mutes()` can put each touched device back.

**Lifecycle hooks** (already wired):

- Recording start (CLI `_cmd_record_body`, GUI `_start_recording`): call `_reconcile_recording_mutes(plan)` AFTER the existing `switch_output(plan.multi_output_name)` block.
- Recording stop / abort / on_close / atexit: call `_restore_all_recording_mutes()` BEFORE `_restore_output_if_needed` so any silenced speaker comes back at the moment dOut returns to the user's physical output.
- Hotplug mid-recording: `AudioDeviceMonitor._recording_branch` re-resolves and re-reconciles when the `(multi_output_name, restore_output_name)` pair changes. Memoized via `self._prev_mute_triple` to avoid redundant work.

**Asymmetric tracking** (important): mute-state changes are recorded asymmetrically.

- When we mute a previously-unmuted device (False→True), we save the original `False` to `_active_mutes`; `_restore_all_recording_mutes()` puts it back to `False` on stop. The user's speakers come back online.
- When we unmute a previously-muted device (True→False) — which happens when the active listening target had a stale system-level mute — we DO NOT save anything. `_restore_all_recording_mutes()` will not re-mute. Rationale: pre-existing mute on a device the user is currently listening through is almost always a leftover state (macOS does not reliably clear device-level mutes across plug cycles); restoring it would put the user back into silence and re-create the same bug they're trying to escape.

**Crash recovery**: every change to `_active_mutes` is mirrored to `CONFIG_DIR / .active_mutes.json` via atomic write (`.tmp` + `os.replace`). At module load, `_recover_persisted_mutes()` reads the file and — if the recorded pid is dead (`os.kill(pid, 0)` raises `ProcessLookupError`) or matches our own pid — restores each device's recorded original then deletes the file. Live concurrent MeetingScribe processes are detected via `_pid_is_alive()` and never touched. The `_atexit_restore_mutes()` handler runs `_restore_all_recording_mutes()` as a final pass on normal exit; it is wrapped to never raise (atexit must not block process exit).

**Diagnostic log tag**: `[MUTE]`. Every reconcile / mute / unmute / persist / recover / restore-all writes a structured line so the daily log alone shows whether the lifecycle behaved correctly. Example trace from a normal start-with-headphones-plug-mid-recording-then-stop sequence:

```
[MUTE] reconcile: active='MacBook Air Speakers' multi_subs=['MacBook Air Speakers'] tracked=[]
[MUTE] device='MacBook Air Speakers' muted (original=False) ok=True
[MUTE] reconcile: active='External Headphones' multi_subs=['MacBook Air Speakers', 'External Headphones'] tracked=['MacBook Air Speakers']
[MUTE] persist: muted={'MacBook Air Speakers': False}
[MUTE] device='MacBook Air Speakers' unmuted (reverting our prior mute; not restoring at stop) ok=True
[MUTE] persist: deleted (no active mutes)
```

## File Naming Convention

All output files share the same stem as the recording:

```
20260512_090120.wav
20260512_090120.raw.txt
20260512_090120.polish.txt
20260512_090120.meeting.md       # written when mode=meeting
20260512_090120.interview.md     # written when mode=interview
20260512_090120.sharing.md       # written when mode=sharing
20260512_090120.meta.json        # calendar sidecar (only when a event was linked)
```

The `.meta.json` sidecar holds the linked calendar event (`title` / `start` / `end` / `attendees` / `location` / `links` / `mode_guess`) and, once the background fetch lands, a `notion` array of `{url, text}`. It lives in `RECORDINGS_DIR` — **outside the repository** — so attendee names never come near version control; mined attendee names go to `hotword.jsonc`, which is already gitignored.

A meeting may have a human-readable suffix as well — `<timestamp>.<custom_name>.<ext>` (e.g. `20260512_090120.客户访谈.wav`). The legacy single-`.md` file (no `.meeting`/`.interview`/`.sharing` infix) is still recognised for read / open / delete.

Suffix routing lives in `_NOTES_SUFFIX` (`meeting` → `.meeting.md`, `interview` → `.interview.md`, `sharing` → `.sharing.md`); `MODES = tuple(_NOTES_SUFFIX.keys())` is the single source of truth driving argparse `choices=`, the mode→label dict in `generate_notes`, and the GUI scanner.

## Common Edit Patterns

**Add a new LLM provider**: add an entry to `DEFAULT_CONFIG["llm"]` (mirrored into `config.jsonc`), add a `_llm_<name>()` runner, and dispatch on its `type` in `_llm_call_one()`. The runner must raise `_LLMCallFailed(kind, message)` on failure and let `_PipelineCancelled` through — a runner that calls `sys.exit(1)` silently opts itself out of the fallback chain.

**Add a new STT provider**: add entry to `DEFAULT_CONFIG["stt"]`, add `_transcribe_<name>()`, dispatch in `transcribe()`.

**Change prompts**: edit `cfg["prompts"]` in `config.jsonc` (the user-facing surface, accepts both `str` and `list[str]`). The built-in defaults live in `_PROMPT_DEFAULTS` (above `DEFAULT_CONFIG`) but per the [Project Rules](#project-rules) section, `_PROMPT_DEFAULTS` is fallback only — every prompt also ships as an editable block in `config.jsonc`, and the two must stay byte-identical. Keys: `polish` is at the top level (mode-agnostic); `notes_zh` / `notes_en` live under `meeting`, `interview`, and `sharing` respectively. All call sites read via `_resolve_prompt(cfg, key, mode=None)`.

To customise just one mode without copy-pasting every default, drop the override into `config.jsonc` — `_deep_merge` keeps the other keys defaulted. For example, to ask the sharing-summary prompt to emphasise code snippets:

```jsonc
{
  "prompts": {
    "sharing": {
      // The literal "{transcript}" token is substituted via str.replace,
      // so other braces in your prompt do NOT need to be escaped.
      "notes_zh": [
        "你是一位技术分享整理助手。请在保留原有结构（分享概览 / 分享正文 / 核心要点 / 最佳实践 / 关键洞察 / 适用边界 / 风险与权衡 / 问答 / 行动建议）的基础上：",
        "- 在「分享正文」中**逐字保留代码片段、命令行、链接**，并用 ``` 围栏标注语言；",
        "- 「最佳实践」按「Do / Don't」两列罗列；",
        "- 「问答」若某问主讲人未直接回答，标注「（未直接回答 / 待跟进）」。",
        "",
        "---",
        "【分享转写】",
        "{transcript}"
      ]
    }
  }
}
```

The `notes_en` side falls back to the default — partial overrides are fine. Both `str` (literal) and `list[str]` (joined on `\n`) are accepted at every prompt slot.

**Modify GUI layout**: widgets live inside `cmd_ui()`'s three interface classes — `RecordingInterface`, `HistoryInterface`, `ConfigInterface` — all wrapped in `MainWindow`. Card surfaces via `_style_as_card(widget, padding=N, name="...")`. Pipeline-button styling via `_apply_open_btn_style(btn, is_open=bool)`.

**Add a translation key**: insert the key into both `_LABELS["zh"]` and `_LABELS["en"]` (top of `cmd_ui()`). Read in widgets via `_t("namespace.key")` or `self._i18n(widget, "namespace.key")` for the static-label callback variant.
