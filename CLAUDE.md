# MeetingScribe — Claude Code Guide

## Project Overview

Single-file Python tool: record audio → FunASR transcribe → LLM polish → meeting notes / interview summary / sharing summary.

- **Entry point**: `meetingscribe.py` (everything in one file)
- **Config**: `config.jsonc` (JSONC with `//` comments, sits next to the script)
- **Output dir**: `~/Documents/meetingscribe/recordings/` (created at runtime)

## Project Rules

These are non-negotiable conventions for this codebase. Violations are bugs even if tests pass.

- **All prompts must live in `config.jsonc`.** Every prompt the pipeline sends to any LLM (currently `polish`, `hotwords_extract`, `caption_mt`, `caption_fix_mt`, `caption_fix_mt_strict`, `caption_review`, and `notes_zh` / `notes_en` for each mode) is shipped as an editable block in `config.jsonc`. The `_PROMPT_DEFAULTS` dict in `meetingscribe.py` is **fallback only** — never the sole source. Rationale: prompts are the main lever for tuning product behaviour, and operations / business / non-Python contributors must be able to read and adjust them without touching code. When you add a new mode or a new prompt slot, you MUST:
  1. Add the default to `_PROMPT_DEFAULTS` (so the tool still works if the user deletes `config.jsonc`), AND
  2. Add the exact same prompt as an editable block in `config.jsonc` with a `//` comment explaining what the prompt is for, AND
  3. Verify with `python3 -c "from meetingscribe import load_config, _resolve_prompt, _PROMPT_DEFAULTS; ..."` that `_resolve_prompt` on the fresh config returns text identical to the `_PROMPT_DEFAULTS` entry — i.e. the jsonc override is a faithful copy, not a drifted variant.

## Running the Tool

```bash
python3 meetingscribe.py ui                              # GUI — PyQt6 + Fluent (needs `python3 -m pip install PyQt6 PyQt6-Fluent-Widgets`)
python3 meetingscribe.py record                          # CLI recording (mode defaults to `meeting`)
python3 meetingscribe.py record --mode interview         # interview mode
python3 meetingscribe.py record --mode sharing           # knowledge-sharing / tech-talk mode
python3 meetingscribe.py transcribe foo.wav --mode sharing  # process existing file as a sharing session
python3 meetingscribe.py devices                         # list audio devices
python3 meetingscribe.py config                          # view/edit config
python3 meetingscribe.py captions foo.wav               # replay a recording through the live caption engine (no sound card)
python3 meetingscribe.py hotwords                        # backfill ASR hotwords from existing .polish.txt/.md (--no-llm / --show)
python3 meetingscribe.py hotwords --notion               # one-off import of member/project/term names from Notion (--dry-run / --min-cjk 3)
python3 meetingscribe.py hotwords --show                 # list + show which terms are next to be evicted
python3 meetingscribe.py hotwords --pin 李雷 GKE         # mark terms never-evictable (--unpin to release)
```

Pipeline modes (`--mode`): `meeting` (default, 会议纪要) | `interview` (面试总结) | `sharing` (分享总结, knowledge-sharing / tech talks with audience Q&A). The set of valid modes is exported as `MODES` in `meetingscribe.py` and enforced by argparse.

## Architecture

The pipeline has four steps, each resumable independently:

```
.wav  →  .raw.txt  →  .polish.txt  →  .<mode>.md
        (FunASR)      (LLM polish)       (LLM notes)
```

`<mode>` is one of `meeting` / `interview` / `sharing` (see "Pipeline modes" above). Each mode lives at a distinct suffix (`.meeting.md` / `.interview.md` / `.sharing.md`) so the same recording can carry summaries for multiple modes side by side.

Each step checks whether its output file already exists and skips if so. This means re-running after a crash resumes from where it stopped.

## Key Functions

| Function | Purpose |
|----------|---------|
| `load_config()` | Reads `config.jsonc`, deep-merges with `DEFAULT_CONFIG` |
| `_log(category, message)` | **File-only diagnostic logger** — writes `[HH:MM:SS] [CATEGORY] msg` to the daily log file. Never touches stdout/stderr by default (use `print()` for user-facing output). `--debug` mirrors lines to stderr. Canonical categories: `REC`/`DEVICE`/`AUDIO`/`HOTPLUG`/`RESTORE`/`STREAM`/`MUTE`/`STT`/`POLISH`/`LLM`/`PIPELINE`/`CONFIG`/`MONITOR`/`CAPTION`/`ERR`/`WARN`. |
| `_QuietCapture(category)` | Context manager that redirects stdout+stderr into buffers and forwards captured lines to `_log()`. Wrapped around FunASR `m.generate()` calls to keep tqdm bars out of the console. Captured lines are ANSI-stripped, and tqdm **progress frames are dropped entirely** (`_is_progress_noise` / `_PROGRESS_NOISE_RE`) instead of being logged: tqdm redraws with `\r` and `str.splitlines()` splits on it, so one caption session buried the log under ~5 000 near-identical bar frames out of 8 583 `[CAPTION]` lines (1.3 MB/day). Real diagnostics (warnings, `rtf_avg`, tracebacks) still land in the log — the timings that were being read off the bars are now logged explicitly by the refine / MT workers. |
| `switch_output(name)` | Switches macOS audio output device via CoreAudio ctypes; **no-op on Windows/Linux** |
| `_log_device_plan(msg)` / `_DEVICE_PLAN_LOG_INTERVAL_SEC` | Throttle in front of the `[DEVICE] plan: …` line. `resolve_audio_devices` re-derives the plan on every monitor tick — once a second while recording, from `MultiStreamRecorder._monitor_iteration`'s fallback — and logging each one made it **37 % of a day's log** (measured: 7 385 lines, 6 191 of the gaps exactly 1 s, and only **3 distinct values** all day). A CHANGE is what carries diagnostic value, so a changed message prints immediately and identical repeats collapse to a heartbeat every `_DEVICE_PLAN_LOG_INTERVAL_SEC` (3 s). Replaying the real day: 7 385 → 2 888 lines (−61 %, 37 % → 14 % of the log). The heartbeat can be raised freely — nothing is lost because changes bypass it (10 s → −82 %, 30 s → −88 %). Deliberately lock-free: two monitor threads clearing the check together cost one duplicate line, cheaper than serialising every device resolution. |
| `resolve_audio_devices(query_fresh)` | **Single source of truth** for mic / system-audio source / restore target. Transport-priority (external > built-in; aggregates/virtual rejected for raw picks). Returns an `AudioPlan` dataclass. Called at start, hotplug, and stop. |
| `_restore_output_if_needed(plan)` | Stop-time restore policy: skips `switch_output` when current default is already a physical device (prevents music-app pause). Falls back through the priority list if the plan's target is missing. |
| `_install_device_listeners()` / `_remove_device_listeners()` | macOS-only CoreAudio HAL property listeners on `kAudioHardwarePropertyDevices` + `…DefaultSystemOutputDevice`. Set the module-level `_hotplug_event` so the recorder reacts within ~100 ms. |
| `AudioDeviceMonitor` | Event-driven daemon thread, started by `cmd_ui` and `cmd_record`. Blocks on `_hotplug_event.wait(timeout=_AUDIO_MONITOR_SAFETY_TIMEOUT_SEC)` (30 s) — no fixed-period polling. Runs one synchronous initial tick on `start()` so the process always syncs to the current best device on launch. **Idle branch** (when `_recording_active` is clear): calls `resolve_audio_devices(query_fresh=True)`; runs `_restore_output_if_needed` on the first tick and on every change to the resolved `(restore_output_name, mic_name, sys_source_name)` triple. **Recording branch**: never switches dOut (would pause music apps) and never refreshes PortAudio (would terminate live streams); but DOES call `resolve_audio_devices(query_fresh=False)` + `_reconcile_recording_mutes(plan)` when `(multi_output_name, restore_output_name)` changes, so the Multi-Output's inactive physical sub-devices stay silenced mid-recording on hotplug. The recorder's own `_monitor` thread remains the authoritative reconciler for input streams. Replaces the older GUI-only `_idle_dout_watchdog`. |
| `MultiStreamRecorder` | N simultaneous `sounddevice.InputStream`s; `_monitor` thread (tracked as `self._monitor_thread`) waits on `_hotplug_event` (or 1 s fallback) and on each wake calls `_monitor_iteration()` which: (1) queries the live PortAudio input device set, (2) re-derives `self.wanted` from `resolve_audio_devices(query_fresh=False)` so mic/system-source swaps mid-recording are honoured (USB headset plugged in → `_close_one` built-in mic, `_try_open` USB mic, pre-swap frames are prepended into the new device's frame list to preserve audio continuity), (3) opens newly-appearing wanted devices and closes disappeared / no-longer-wanted ones. `start()` sets the module-level `_recording_active`; `stop()` clears it in a `finally`. `stop()` **joins** `self._monitor_thread` (2 s timeout) BEFORE clearing `self._streams`, eliminating the race where `_monitor_iteration`'s `_try_open` could reset `self._frames` mid-stop and discard captured audio. `_try_open` defensively re-checks `self.recording` inside its lock and discards orphan opens with `[STREAM] discarded post-stop open of device=…`. Emits `mic-not-opened` / `system-audio-not-opened` warnings via `on_warning` and the `[WARN]` log category — warnings are log-only by design; no sidecar `.warnings.txt` is written. |
| `LiveCaptionEngine` | Live bilingual captions during recording (GUI only, fully local). `feed()` and `MultiStreamRecorder.save()` **downmix all of a device's channels** (mean) rather than keeping channel 0: the old behaviour silently discarded content, which is why replaying a role-separated stereo recording through BlackHole produced garbage captions — the speech sat on channel 1, the digital copy read as RMS 0.0000, and the captions actually came from the microphone re-recording the loudspeakers through the air. The same loss would hit a hard-right-panned participant in a live call. Lifecycle `start()` → `feed(role, frames, sr)` from `MultiStreamRecorder.on_audio_chunk` → `stop()`. Three worker threads: ASR (drains per-source ring buffers every 250 ms, mixes to 16 kHz mono, feeds the streaming backend), MT (preloads its model at engine start; translates finalized segments off a queue, and on idle ticks opportunistically translates the in-flight partial — `partial_translation` events, ≥6-char gate), and refine (`live_captions.refine`): re-decodes each finalized segment's audio with the offline FunASR stack in the background, emits `refined` to replace the caption line and re-queues its translation. **English-dominant segments skip the refine pass entirely** (`_caption_is_english`): it re-decodes with `paraformer-zh`, a CHINESE model, so on English it does not correct but corrupt — a real session (2026-08-26 15:15) logged `changed=True` on 53 of 56 English segments at 1.7–2.5 s each, which is exactly the "refine does nothing useful" the user reported. A re-decode measures ~1.0–1.4 s on M2 (2.5 s on long segments), so `_finalize_segment` also **drops** segments once the refine queue holds `refine_max_backlog` (default 3) — an unbounded queue delivered corrections minutes after the line scrolled away. Every pass logs `[CAPTION] refine seg=… took=…s chars=A→B changed=…` and every drop logs `refine skipped seg=… (backlog=…)`, so a session's `changed=True` ratio tells you whether the pass earns its cost. Events surface via `on_event(dict)` — `status` / `error` / `partial` / `partial_translation` / `final` (carries `role`) / `refined` / `translation` — emitted from worker threads; the GUI re-emits them through `_RecorderState.caption_event` (queued Qt signal). **Sentence breaking is configurable** (`live_captions.endpoint` → `_caption_endpoint_rules`, forwarded to sherpa): `rule2_min_trailing_silence` is the main knob — how much trailing silence ends a line once text has been decoded. It was hardcoded at 0.8 s, i.e. MORE aggressive than sherpa's own 1.2 s default, so a continuous speaker got cut into more, shorter lines than stock. **1.2 is now the default, chosen by measurement** on one 4-minute passage of continuous single-speaker speech (0.8 → 18 lines / 75.8 chars mean; 1.2 → 14 / 97.6; 1.6 → 14 / 95.4). 0.8 → 1.2 is 22 % fewer lines and 29 % longer ones with total characters 1365 vs 1366 — the same content cut differently, nothing lost — and 1.2 → 1.6 does not change the line count at all, so it has plateaued and raising it further buys nothing. Fewer lines is the win that matters downstream, since a review call costs 41.6 s fixed against only 3.4 s per line. Longer lines carry more context into the refine and review passes (both correct better) and cost fewer LLM rows per minute, at the price of the line appearing later. `rule1` applies before any text is decoded, `rule3_min_utterance_length` caps how long one line may grow. Values are clamped to `_CAPTION_ENDPOINT_BOUNDS` and logged, so a junk config value can't silently disable sentence breaking, and they are part of the ASR cache key, because they are baked into the recognizer at construction — without that an A/B in one process would reuse the first set. A/B with `captions <wav> --rule2 …`, which reports lines/minute, mean line length and resulting review batches. **One recognition path**: sherpa-onnx streaming zipformer zh-en (auto-downloaded tarball via `_ensure_sherpa_model`, ~320 ms) + opus-mt Marian, with finalized lines re-decoded by the batch pipeline's cached `paraformer-large`+vad+punc stack (`refine`). The former **accurate mode** (`_FunASRCaptionASR`: `paraformer-zh-streaming` partials + energy endpoint → offline 2pass, paired with NLLB) is DELETED along with `live_captions.mode` and the `fast` / `accurate` config nesting: its streaming model is Chinese-only and measurably worse on the English meetings this is used for, and having two ASR paths doubled the surface every caption fix had to be applied to. NLLB survives as an explicit `mt_provider: "nllb"` choice reading its own `live_captions.nllb` block, since it measurably beats opus-mt on some domain terminology. MT provider is switchable via `live_captions.mt_provider`: `"qwen"` (the `DEFAULT_CONFIG` value; **the shipped `config.jsonc` sets `"default"`** = opus-mt — flip it to `"qwen"` to exercise the correction path) loads `_QwenCaptionMT` — a local Qwen 1.5B instruct GGUF via llama.cpp (`_ensure_qwen_gguf` auto-download, prompt from `_resolve_prompt(cfg, "caption_mt")`), which injects any `stt.funasr.hotword` terms found in the source line as a keep-verbatim glossary; on ANY load failure (llama-cpp-python missing, model missing) it logs and falls back to opus-mt Marian. Cached qwen backends get `set_hotword()` refreshed on reuse. **Finalized lines** additionally go through `correct_and_translate` (`qwen.correct`, default on): ONE combined call that first repairs obvious ASR errors (homophones / broken English words like `lang 三姆斯`→`LangSmith`) using the last 3 finalized lines as rolling context (`_mt_context`) + a **line-scoped** glossary, then translates. `_glossary_candidates(text, hotwords, limit)` picks that glossary: literal (case-insensitive) hits first, then fuzzy near-misses — a hotword qualifies only if it shares a ≥3-character run with one of the line's alnum / CJK-flanked-alnum spans (≥3 chars) AND scores SequenceMatcher ≥ 0.45, and spans already covered by a literal hit are excluded from fuzzy matching. Capped at `qwen.glossary_max` (12). Rationale, all measured against the real 100-term table: dumping the whole table was the main driver of the model applying unrelated terms; ratio alone let `dora` pull in `RMA`/`Portland`; without the literal-coverage rule `用 LangGraph` also dragged in LangSmith/LangChain/LangFuse. Pure-CJK terms are literal-match only — `里雷`→`李雷` would need pinyin, which is not a dependency here. The MT worker emits the corrected line as a `refined` event before the `translation`. `_parse_fix_mt` guards against small-model failure modes: missing 翻译： line → whole reply used as plain translation; corrected line outside 0.66x–2.0x of the original length OR SequenceMatcher similarity < 0.5 → discarded (catches dropped clauses and translation-in-修正-line; a bare prefix scores HIGH on similarity, which is why the length bound exists). **Output shape is pinned by a GBNF grammar** (`qwen.grammar`, default on): `_FIX_MT_GRAMMAR` forces `修正：<≤400 chars>\n翻译：<≤400 chars>`, which structurally kills example leakage and repetition loops. Grammar on → the **zero-shot** prompt `caption_fix_mt_strict` is used; grammar unavailable (older llama-cpp-python without `{m,n}` bounded repetition → `LlamaGrammar.from_string` raises, logged under `[CAPTION]`) or `grammar: false` → the **few-shot** `caption_fix_mt`. Both prompts must stay rule-identical; only the format example differs. The few-shot example exists because abstract format rules alone made the 1.5B model leak translations into the 修正 line — do not delete it, and do not delete the strict variant either: a 1.5B model copies example wording into its own output, which is why the example goes away once the decoder enforces the format. Measured on M2 Metal (q4_K_M, min of 3): grammar costs **1.22 s → 1.80 s** per finalized line, while prompt length is noise (few-shot 1.15 s vs zero-shot 1.22 s). The plain `translate()` path is deliberately **not** grammar-constrained — it also serves in-flight partials (+0.30 s there, 0.42 → 0.72 s) and has no structure to enforce. **Do not switch an English-source meeting to qwen**: measured on 4 real English caption lines, the 1.5B model returned the corrected ENGLISH as its 翻译 line in 3 of 4 — it corrects well but does not reliably translate en→zh at this size, while Marian at least always produces Chinese. `mt_provider` accepts `"marian"` (default, aliases `opus` / `opus-mt`) / `"nllb"`, cached under `("mt", want)` so both can coexist. On domain terminology the two trade wins (measured): NLLB kept `PoC` and `包裹` where opus-mt produced 「钻石交易市场」and 「土地」, opus-mt kept `RFP` where NLLB dropped a letter; NLLB costs 760–1200 ms/line against 120–150 ms. `_glossary_candidates` skips FUZZY matching on English-dominant lines (literal hits only): English words share 3-character runs with unrelated hotwords constantly — `"…were told about this RFP around four day"` matched `Acme` via `were`/`ere`, and one line pulled in eight terms. Heavy backends are cached in module-level `_caption_backend_cache` across recording sessions (`reset_session()` rebinds callbacks + clears per-session state). Finalized/refined text **and the in-flight partial** both pass through `_caption_tidy_zh` (drops pure fillers 嗯/呃/哎呀/唉 per `_CAPTION_FILLERS` — grammatical particles 呢/啊/吧 stay; collapses stutter n-gram repeats 「所以就像所以就像」→「所以就像」; sweeps orphan punctuation) so the translation input is clean too. **Chunk-boundary dedup** (`_append_hypothesis`) attacks the same duplication at its source. Streaming decoders are append-only — once a token is emitted it is never revised — so a syllable split across a chunk boundary gets committed twice. Measured on 18 s of real audio: the streaming pass produced 129 chars where the offline pass produced 101 (+28 %), i.e. the speaker did not say 28 of those characters. Since the duplicate sits at the JOIN, `_SherpaCaptionASR._advance_hypothesis` keeps the recognizer's raw hypothesis (`_raw_hyp`) separate from our deduped one (`_clean_hyp`), isolates each chunk's delta, and runs it through `_dedup_caption_boundary`; a recognizer that rewrites earlier text (a rescoring build, not the append-only behaviour measured here) is trusted wholesale rather than splicing two disagreeing histories. Measured result on the same slice: 129 → 124, and 115 after the collapse layer, against the 101 offline baseline. The 2-character minimum overlap stays: relaxing it to 1 bought exactly ONE more character while risking a genuine 「看看」 split at the join, because the remaining repeats (做做 / 动动 / 成成) are INTRA-chunk — emitted inside a single delta, where boundary logic structurally cannot see them — and homophone substitutions (在→再) are not textual duplicates at all. Tidying the PARTIAL matters as much as the final: a streaming decoder oscillates between hypotheses while a sentence is still open, and measured on one real meeting the partial line carried 4-19x the duplication of the offline transcript of the SAME audio (single-char repeats 85 vs 21 per 1000 chars, triples 25 vs 1.3, 2-char word repeats 55 vs 5.4) — 「大大大家大家」/「在在在在」/「训练练练习」 were on screen verbatim because the collapse only ran at finalize. It now runs in `_emit_partial`, which also gives the opportunistic partial translation a clean input. The remaining 2-char single-char repeats (说说 / 高高 / 年年) stay ON PURPOSE — Chinese reduplication is legitimate, so `_CAPTION_STUTTER_2CHAR` only lists characters that never reduplicate; for Chinese finals the refine re-decode brings duplication down to offline levels anyway. English additionally goes through `_caption_fix_case`: the streaming zipformer emits ALL CAPS (`AND THEN OKAY WERE CON YEAH`), which read as shouting next to the mixed-case lines the refine pass produced for the same session. Only fully upper-case text is touched (any lowercase → left alone, so `这个 GKE 集群` keeps its acronym), hotwords get their configured spelling back, and standalone `I` / `I'll` stay capitalized. **Translation output** goes through `_collapse_mt_repeats`: greedy decoding (num_beams=1, chosen for latency) degenerates into loops on noisy ASR input — one real line came back as 「雅 的 内容」×30 then `Ya`×100. The primary fix is decode-side (`no_repeat_ngram_size=_MT_NO_REPEAT_NGRAM` (6) + `repetition_penalty=_MT_REPETITION_PENALTY` (1.15) on both Marian and NLLB `generate()`); the collapse is the display-side backstop. Its thresholds are asymmetric by design: word-level rules run first and need 3+ repeats so English keeps `very very`, and character-level rules (long n-grams at 2+) are skipped for English entirely — they would eat `very very` as the 5-char n-gram `very `. `stt.funasr.hotword` is shared with captions: it biases sherpa decoding (modified_beam_search + hotwords_file + `cjkchar+bpe`/bpe.vocab, graceful greedy fallback on old sherpa builds; cached recognizer → hotword edits need an app restart). **The hotwords file is ONE TERM PER LINE and a line may contain spaces** — sherpa encodes the whole line as a token sequence, verified against the real model for `Cloud SQL` / `error budget` / `node pool` / `Spot VM`. It used to split on whitespace, which made multi-word terms structurally inexpressible, and most GCP service names are two words. Phrases live in a separate `phrases` array in `hotword.jsonc` (`_hotword_term_list` merges the two) because the flat `hotword` string is space-separated and cannot hold one; keeping it that way leaves every existing consumer untouched and only the phrase-capable ones (sherpa file, qwen glossary, `_caption_fix_case`) read both. **`_sherpa_encodable` filters terms the model cannot encode and logs them**: the cjkchar+bpe vocabulary has no punctuation tokens, so ONE stray character makes the recognizer skip the whole term — and it complains on C-level stderr, which the log tee never captured, so a term looked configured while biasing nothing. Measured: letters / digits / CJK / spaces encode; `.` `+` `_` `'` `-` `/` all fail, which silently disabled `AI-Native` / `Agent-Ready` / `Semi-Annual` / `one-liner` and rules out `Pub/Sub` and `blue-green`. Those terms still reach the refine pass and the qwen glossary, which take the raw string. Manage phrases with `hotwords --phrase "Cloud SQL"` / `--unphrase`, the refine pass forwards it as FunASR `generate(hotword=…)`. NLLB gets dynamic int8 quantization by default (`nllb.mt_int8`); partial-line translation is skipped whenever **the last partial translation** took >0.8 s (`_mt_partial_secs`, tracked separately from `_mt_last_secs`) so finals never queue behind a slow partial — gating on the shared last-call time instead would let the grammar-constrained fix call (~1.8 s) silently switch partial translation off for the rest of the session. Each finalized line logs `[CAPTION] mt seg=… took=…s corrected=… out_chars=…`. All backend imports are lazy with pip-hint `RuntimeError`s; captions failing never affects recording (the audio tap swallows exceptions). Config block: `live_captions{enabled, partial_interval_ms, merge_gap_ms, history_minutes, history_max, render_debounce_ms, speaker_labels, speaker_id{…}, review{…}, mt_provider, asr_model_dir, mt_zh_en, mt_en_zh, refine, refine_max_backlog, nllb{mt_model, mt_int8}, qwen{model_repo, model_file, model_path, n_ctx, threads, n_gpu_layers, correct, grammar, glossary_max}}` (`n_gpu_layers: -1` = full Metal offload by default — keeps Qwen off the CPU). **Speaker identification** runs at two levels. (1) `live_captions.speaker_labels` (default on) — the cheap channel guess: `_drain_mixed` tallies per-source energy and `_take_segment_role` attributes each finalized segment to the louder source. Energy is scored RELATIVE to each source's own running peak (`_role_peak`, 0.999 decay), because a mic at -30 dBFS and a playback stream at -6 dBFS aren't comparable in absolute RMS — comparing them raw tagged almost every line 对方. (2) `live_captions.speaker_id` (default on) — the real answer: a fourth worker thread (`_speaker_worker`, queue capped at `max_backlog`) runs `_CaptionSpeakerId` (cam++ `iic/speech_campplus_sv_zh-cn_16k-common`, ~27 MB auto-download, 192-dim embedding in **60 ms** per segment) and feeds `_SpeakerClusterer`, an online cosine clusterer. That is what separates the several people sharing the single system-audio stream — channel role structurally cannot, since everyone on the call arrives mixed. Measured on cam++'s own sample voices: same speaker 0.694, different speakers -0.084 / 0.007, hence `threshold: 0.5` (clear of both, with margin for real VoIP audio scoring below clean studio samples). Centroids are running means; past `max_speakers` a new voice folds into the nearest cluster instead of growing forever. **A cluster must accumulate `speaker_id.min_segments` (2) segments before it is shown as a person**: `display_number` returns `None` until then and `_speaker_worker` HOLDS those segment ids in `_spk_pending`, tagging them retroactively if a second segment joins — so a real speaker loses only a few seconds' delay, while a cough that decoded to one line never mints a 说话人N at all. Measured need: on one real 34-minute meeting 4 of 8 clusters held exactly one segment each, and they consumed `max_speakers`, so genuinely new voices arriving later got folded into existing speakers. Numbers are handed out in QUALIFICATION order, not discovery order — discovery order would leave gaps (说话人1 then 说话人3 because cluster 1 never earned a number), which reads as a bug. Numbering is GLOBAL across both channels: reserving 我 for the mic side broke as soon as two people shared one microphone — a meeting room — since both scored a mic majority and both got labelled 我. `majority_side` therefore reports a SIDE, not an identity, and is used only to tint the tag (blue for our side); identity comes from the voice print alone. Verified with real voices: two speakers alternating on the SAME mic channel get 说话人1 / 说话人2 stably, 2 clusters total. Segments shorter than `min_secs` (1.0 s) are skipped — too little audio for a reliable print. Junk segments are dropped even earlier, in `_finalize_segment` via `_caption_is_noise`: the streaming model emits a stray letter or particle for a cough or a keyboard tap, and on a real 34-minute meeting those lines (`M`, `N`, `A`, `啊。`) became 4 of the 8 clusters — one segment each — exhausting `max_speakers` so genuinely new speakers later got folded into existing ones. The filter drops a line whose punctuation-stripped core is empty, is a single ASCII letter, or consists only of `_CAPTION_NOISE_ONLY` interjections; short real answers (对 / 好 / 可以) are deliberately NOT in that set. A dropped segment consumes no segment id and reaches neither the pane, MT, refine nor the voice print. The ASR backend forwards segment audio (`_emit_final(text, audio)`), which is what the voice print consumes. The `speaker` event arrives ~60 ms after `final`, so a line's tag flips from the channel guess `[对方]` to `[说话人2]`; `_group_caption_rows` splits on `(speaker, role)` so a paragraph never mixes people. When speaker id is off or a segment is shorter than `min_secs`, the side tag is all a line gets (`mic` → 我方 / `system` → 对方 — a side, not a person — rendered as a coloured tag and re-translated on language switch). Returns `None` — no tag at all — until ≥2 sources have been heard above `_CAPTION_ROLE_RMS_FLOOR`, because tagging every line in a solo recording is noise. "Heard" tests the source's session PEAK, not the current window, and the floor is 0.002: at 0.01-per-window a built-in mic never qualified, so a real session logged `side=None` for all 208 segments and the tag never got its colour. `_group_caption_rows` also refuses to merge across a role change, so a paragraph never attributes one side's words to the other. The offline `stt.funasr.spk_model` (cam++ on the whole recording) remains the higher-accuracy path for the transcript, since it clusters with the full file in hand. **Periodic batch re-check** (`live_captions.review`, default on): a fifth worker thread (`_review_worker`) wakes every `interval_minutes` (5), pops up to `max_lines` (120) buffered finalized rows via `_take_review_batch`, and sends them — WITH their current translations — to a full-size LLM through `_review_llm` (`review.provider`, empty = `polish_provider`). This is the only pass with cross-line context: no per-line mechanism can know that 「拆特ops」 three lines back and 「ChatOps」 now are the same term, and the offline notes for the same meeting prove how much a big model recovers (`巡检` / `CockroachDB` / `flexible CUD` all correct there, all wrong in the live pane). Prompt `caption_review` gets `{hotwords}` + `{lines}` (`N ||| 原文 ||| 当前译文` via `_format_caption_review_lines`); `_parse_caption_review` reads `N ||| 修正后的原文 ||| 译文` back, keyed by SEGMENT ID not position. It is defensive by design because it rewrites lines the user has already read: an unknown index, an empty field, or a correction outside 0.5x–2.0x length / SequenceMatcher < 0.45 leaves that line's source untouched (the translation is still taken — it legitimately looks nothing like the source), and an omitted entry means that row goes BACK to the front of the buffer for another round (bounded by `review.max_tries`, 2) — without that, a truncated reply would drop lines from review permanently, since the batch was already popped. Batch sizing is bound by OUTPUT tokens, not the context window: the model re-emits every line, measured at 42 chars/line on a real meeting → 120 lines ≈ 5.6k in / 5.2k out, just under the common 8k output ceiling, while the measured cadence of 6.1 finalized lines/minute puts only ~30 lines in a 5-minute interval. So `max_lines: 120` is ~4× headroom; raising it buys nothing and courts truncation. Corrections surface as the ordinary `refined` + `translation` events, so the GUI needs no special case; a batch touching rows minutes back makes `_CaptionDocRenderer` rewrite that tail once per interval. Rows are buffered on finalize (`_review_record`) and their translations tracked (`_review_record_translation`), with the acoustic refine pass updating the buffered text in place so the LLM reviews the latest version. **The buffer is capped** (`review.max_buffer`, 240): `max_lines` bounds one BATCH only, so without this a stalled provider grows memory without limit and the pass stops being useful — a correction landing 40 minutes after the line scrolled away is not worth showing. Over the cap the OLDEST rows go (they scrolled off screen long ago; under sustained overflow keeping the recent window is what preserves any value) and every drop is logged with its id range, never silently — a pass reporting `batch=8 parsed=8` while having discarded rows reads as full coverage. One batch of backlog logs an early warning first, once per crossing rather than per row. `_trim_review_buffer` enforces it on both the append and the requeue path, since putting missed rows back at the front can push the buffer over on its own. **Each batch also gets read-only context** (`review.context_lines`, 12 — `_format_caption_review_context` into the prompt's `{context}` slot): the settled text of the lines this pass already corrected. Cross-batch terminology consistency needs it, since batch N settling on 「ChatOps」 is useless if batch N+1 independently picks 「拆特ops」 again. Those lines are reference only, never re-corrected — the user already saw them corrected and rewriting them every interval would churn the pane. They are deliberately NOT rendered in the numbered `N ||| … ||| …` shape: reply indices are POSITIONAL into `batch`, so a model echoing a context line in that format would land its text on an unrelated segment; an unnumbered bullet gives it no template to copy. Cost is input tokens only, and the measured per-call cost is **41.6 s fixed + 3.4 s per line** (linear fit over 80 real batches, R²=0.17 — batch size barely predicts duration, the fixed cost dominates), so a dozen reference lines is noise. That same fixed cost is why `review.interval_minutes` matters more than anything else here: at 1 minute you pay it ~51 times in a 51-minute meeting (measured 94 % LLM duty cycle, 17 % headroom); at 3 minutes ~17 times. Cost: one LLM call per interval while recording; `enabled: false` keeps captions fully local. No flush on stop — the offline pipeline reprocesses the whole recording far better anyway. **Every rewrite is logged with its before/after**, one greppable line per change — the pass silently edits lines the user already read, so aggregate counts alone would make it unauditable:
```
[CAPTION] review seg=2 src: 「Adb主要是BBQ和cr circle这两个优化的措施」 → 「DBA 主要是 BBQ 和 CockroachDB 这两个优化的措施」
[CAPTION] review seg=2 dst: 「Adb was mainly implemented as…」 → 「On the DBA side it's mainly…」
[CAPTION] review batch=4 parsed=4 src_changed=3 dst_changed=3 requeued=0 took=48.3s
```
`_review_log_text` flattens whitespace so one change is one line, brackets the value with 「」 so field edges survive text containing arrows or colons, and caps a runaway line at 500 chars with a `…(+N)` marker. Unchanged lines log nothing. Note for later comparison: the daily log is purged after 7 days by `_purge_old_logs`, so copy it out for longer retention. Log tag `[CAPTION]`. |

## Config System

- **`hotword.jsonc` carries bookkeeping, not just a string.** `_load_hotword_store()` / `_save_hotword_file(hotword, store)` read and write `hotword` (the space-separated list, still the first key and still hand-editable), `pinned`, `hits`, `last_seen` and `epoch`. A flat `{"hotword": "a b c"}` file — everything written before this existed, and anything a human edits — loads as all-rolling with no history, and the flat key is always written, so older builds keep working. A `pinned` entry missing from `hotword` is still added to the list, so pinning a name is a one-line edit rather than two.
- **`hotword.jsonc` is separate and gitignored.** The hotword list is auto-mined from every meeting, so it fills up with colleague names, customer names and internal codenames — local data that must not ship with a public repo. `config.jsonc` keeps `stt.funasr.hotword` as an empty default; `_load_hotword_file()` overrides it at load time when `hotword.jsonc` has content, `_persist_hotwords` writes THERE, and `_migrate_inline_hotword` blanks any legacy inline value in `config.jsonc` on the next extraction so a stale copy can't linger in a tracked file. Only `hotword.jsonc.example` is committed. A broken hotword file is logged and ignored, never fatal — no contextual biasing beats no recording. **Tests must redirect `HOTWORD_FILE`**, not just `CONFIG_FILE`: forgetting to overwrote the developer's real list with two-word fixtures, which is why `tests/test_hotwords.py` has an autouse fixture pinning it into `tmp_path`.
- `config.jsonc` is parsed with `_strip_jsonc_comments()` (regex strips `//` lines)
- `_deep_merge(DEFAULT_CONFIG, on_disk)` — nested dicts merge recursively; on-disk values win
- `load_config()` never auto-writes back; `save_config()` writes plain JSON (comments lost)
- CLI flags override config at runtime but never persist

Bookkeeping is by BLOCK NUMBER — each group is exactly `_BLOCKS_PER_GROUP` (2) paragraphs, so group *i* starts at block *2i* and `blockCount == 2 × len(committed)` is checked before every patch; a violation, a divergence with no untouched leading group (`k_eff < 1`), or an invalid block falls back to a full `setHtml`, so a bookkeeping bug can only cost performance, never a corrupted pane. Appends deliberately rewrite from the LAST committed group rather than inserting at the document end: block `2k` does not exist yet when appending, and `insertHtml` at the end merges inline into the previous block (verified — it produced 3 blocks where 4 were expected). Measured with real Qt: on a 12 000-group document an append costs **0.5 ms** and a tail edit **0.4 ms**, against **140 ms** for `setHtml`. Simulating whole 4-hour sessions end-to-end (rows → prune → group → render, two renders per line): full rebuilds are 0.2–0.8 % of renders at 15/30/66 lines-per-minute, average render 0.15–0.23 ms. The view follows the tail only when the user is already scrolled to the bottom (≤8 px margin) so scrolling back during a session works. **Retention is by TIME**: `_prune_caption_rows` drops rows older than `live_captions.history_minutes` (default 180 = 3 h of scroll-back), with `history_max` (12 000) as a pure memory backstop — a row cap alone can't promise a duration, since 3 h is 2 700 rows at 15 lines/min but 11 887 at 66. Eviction is BATCHED (`slack_secs=60` / `slack_rows=200`) and that is load-bearing, not a micro-optimization: dropping one row per append shifts every paragraph, so group 0 changes and the renderer can no longer patch — the pane would re-layout in full on every line once the window fills. Batching turns that into ~1 rebuild/minute (the measured 0.2–0.8 %). The window is therefore a *minimum*; up to the slack of extra history may be retained. Engine events arrive on the Qt thread via `state.caption_event` → `_on_caption_event`, **through a per-session gate**. `_RecorderState` bumps `_caption_session` on every `start_recording` and hands the engine a closure that drops events whose captured token is no longer current. Load-bearing for stop-then-immediately-start: `stop()` cannot interrupt an in-flight worker call, and the log shows the review worker emitting 6 rewrites **23 s after** `engine stopped` (2026-08-27 16:21:33). Segment ids restart at 1 every session and `_on_caption_event` matches `refined` / `translation` / `speaker` by id ALONE, so a late correction lands on the NEW session's row with that id — and the review buffer pops oldest-first while running a batch behind, so the ids in flight at stop time are precisely the early ones the next session immediately produces. The token is compared rather than the engine's running flag, so the session being stopped still delivers its ASR-flush tail. `stop()` itself is budgeted per role (`_CAPTION_STOP_ASR_TIMEOUT` 5 s, `_CAPTION_STOP_TOKEN_TIMEOUT` 0.5 s for the rest): five threads at a flat 5 s could block the Qt thread for 25 s on every stop. The ASR thread keeps the real budget because it shares the cached streaming recognizer with the next session, and interleaving two sessions' audio into one decoder stream corrupts recognition rather than merely delaying it; the others are abandoned after a token wait and logged, since their late events are now harmless. `_start_recording` clears the pane and pushes the switch into `_RecorderState.captions_enabled`; `_RecorderState` owns the `LiveCaptionEngine` lifecycle around the recorder.
- Markdown callouts: the meeting-mode notes prompts instruct the LLM to emit GitHub/Obsidian-style callout blockquotes (`> [!important]` decisions, `> [!tip]` action items, `> [!warning]` risks). Qt's `setMarkdown` renders these as plain quotes with the literal `[!type]` text, so every notes render in `HistoryInterface` goes through `_set_body_markdown(md)` → `setMarkdown` + `_apply_callout_styles(doc)`. The post-pass finds blockquote blocks via the `BlockQuoteLevel` block property, paints each callout run with a colored card background, and replaces the literal marker with a bold colored icon+title (a `U+2028` line separator keeps the body on its own line — Qt merges `> [!type]\n> body` into a single paragraph via soft line break). Type→style map is `_CALLOUT_STYLES` (note / tip / todo / important / warning / caution; unknown types get a gray 💬 fallback). Plain blockquotes without a marker are left untouched. Raw/polish text views (`setPlainText`) are unaffected.

## Platform Notes

- **macOS**: Full support. `switch_output()` uses CoreAudio ctypes to auto-switch audio devices around recording.
- **Windows**: `switch_output()` is a no-op. User sets up VoiceMeeter Banana + VB-Audio Virtual Cable manually. Use `os.startfile()` to open result files.
- **Linux**: Untested. `switch_output()` is a no-op. `xdg-open` used for result files.

### macOS music-pause behavior on recording

Recording system audio requires routing playback through the Multi-Output Device (which tees to BlackHole for capture). The recording start/stop paths therefore change `kAudioHardwarePropertyDefaultOutputDevice` (`dOut`) twice per session: physical → Multi-Output at start, Multi-Output → physical at stop. macOS delivers a default-output-changed event on every `dOut` write, and many audio apps (Apple Music, Spotify, Safari, Chrome) react by pausing playback.

To make this workflow music-pause-free, the start path is **conditional**: if the user's permanent `dOut` is already the Multi-Output Device, the start-time switch is skipped. The `_recording_did_switch` event tracks whether the start path actually performed a switch; `_restore_output_if_needed(plan, reason="post-recording")` only runs when the event is set. Idle-state callers (`AudioDeviceMonitor`) bypass the gate via `reason="idle-event"` so hotplug-driven `dOut`+`sOut` alignment still works.

**Lifecycle ordering** (important for maintainers): `_recording_did_switch` is cleared at the **entry of the recording-start lifecycle** in both `cmd_record` and `cmd_ui` — BEFORE the start-time `switch_output` decision. The start path sets the flag only when `switch_output(multi_output_name)` actually runs. `MultiStreamRecorder.start()` does NOT touch the flag (clearing it there would wipe the bit set moments before by the start-path switch).

**Recommended user setup for zero music pauses:**
1. In *Audio MIDI Setup*, configure the Multi-Output Device to contain only `[BlackHole 2ch, your preferred physical output]` (e.g. BlackHole + External Headphones). Including multiple physical outputs causes audio to play through all of them simultaneously.
2. Right-click the Multi-Output Device in Audio MIDI Setup and set it as the macOS default output.
3. Now MeetingScribe's start/stop are silent — `_recording_did_switch` stays clear and music apps see no device change.

**Known limitation**: when the permanent `dOut` is a physical device (the default macOS setup most users have), bugs 1 and 3 of the music-pause report are intrinsic to the dOut-switching strategy and cannot be eliminated without a different recording stack (a dynamic session-scoped aggregate, rejected in `robust-audio-device-handling`; or `SCStream` screen-capture-with-audio, out of scope).

### macOS per-device mute lifecycle (Multi-Output sub-devices)

When the user's Multi-Output Device fans out to BOTH speakers AND headphones simultaneously (sub-list includes `BuiltInSpeakerDevice` + `BuiltInHeadphoneOutputDevice`), plugging in headphones during a recording causes audio to play from both at once. The fix is to mute the inactive physical sub-device(s) for the duration of the recording — leaving `dOut` unchanged (no music pause) while BlackHole capture continues uninterrupted.

**Helpers** (`meetingscribe.py`):

- `_ca_get_device_mute(name)` / `_ca_set_device_mute(name, muted)` — CoreAudio `kAudioDevicePropertyMute` accessors, output scope, master element. macOS only.
- `_get_multi_output_physical_subs(name)` — reads the Multi-Output's `kAudioAggregateDevicePropertyComposition` CFDictionary (we use `acom`, not `agdv` — the latter returns `kAudioHardwareUnknownPropertyError` on at least some macOS versions), extracts each sub-device's UID, looks up the matching device name, filters out virtual / aggregate transports.
- `_reconcile_recording_mutes(plan)` — for each physical sub of `plan.multi_output_name`, ensures `desired = (sub != plan.restore_output_name)` matches the device's current mute state. Wires the lifecycle through `_active_mutes: dict[name, original_bool]` so `_restore_all_recording_mutes()` can put each touched device back.

**Lifecycle hooks** (already wired):

- Recording start (CLI `_cmd_record_body`, GUI `_start_recording`): call `_reconcile_recording_mutes(plan)` AFTER the existing `switch_output(plan.multi_output_name)` block.
- Recording stop / abort / on_close / atexit: call `_restore_all_recording_mutes()` BEFORE `_restore_output_if_needed` so any silenced speaker comes back at the moment dOut returns to the user's physical output.
- Hotplug mid-recording: `AudioDeviceMonitor._recording_branch` re-resolves and re-reconciles when the `(multi_output_name, restore_output_name)` pair changes. Memoized via `self._prev_mute_triple` to avoid redundant work.

**Asymmetric tracking** (important): mute-state changes are recorded asymmetrically.

- When we mute a previously-unmuted device (False→True), we save the original `False` to `_active_mutes`; `_restore_all_recording_mutes()` puts it back to `False` on stop. The user's speakers come back online.
- When we unmute a previously-muted device (True→False) — which happens when the active listening target had a stale system-level mute — we DO NOT save anything. `_restore_all_recording_mutes()` will not re-mute. Rationale: pre-existing mute on a device the user is currently listening through is almost always a leftover state (macOS does not reliably clear device-level mutes across plug cycles); restoring it would put the user back into silence and re-create the same bug they're trying to escape.

**Crash recovery**: every change to `_active_mutes` is mirrored to `CONFIG_DIR / .active_mutes.json` via atomic write (`.tmp` + `os.replace`). At module load, `_recover_persisted_mutes()` reads the file and — if the recorded pid is dead (`os.kill(pid, 0)` raises `ProcessLookupError`) or matches our own pid — restores each device's recorded original then deletes the file. Live concurrent MeetingScribe processes are detected via `_pid_is_alive()` and never touched. The `_atexit_restore_mutes()` handler runs `_restore_all_recording_mutes()` as a final pass on normal exit; it is wrapped to never raise (atexit must not block process exit).

**Diagnostic log tag**: `[MUTE]`. Every reconcile / mute / unmute / persist / recover / restore-all writes a structured line so the daily log alone shows whether the lifecycle behaved correctly. Example trace from a normal start-with-headphones-plug-mid-recording-then-stop sequence:

```
[MUTE] reconcile: active='MacBook Air Speakers' multi_subs=['MacBook Air Speakers'] tracked=[]
[MUTE] device='MacBook Air Speakers' muted (original=False) ok=True
[MUTE] reconcile: active='External Headphones' multi_subs=['MacBook Air Speakers', 'External Headphones'] tracked=['MacBook Air Speakers']
[MUTE] persist: muted={'MacBook Air Speakers': False}
[MUTE] device='MacBook Air Speakers' unmuted (reverting our prior mute; not restoring at stop) ok=True
[MUTE] persist: deleted (no active mutes)
```

## File Naming Convention

All output files share the same stem as the recording:

```
20260512_090120.wav
20260512_090120.raw.txt
20260512_090120.polish.txt
20260512_090120.meeting.md       # written when mode=meeting
20260512_090120.interview.md     # written when mode=interview
20260512_090120.sharing.md       # written when mode=sharing
```

A meeting may have a human-readable suffix as well — `<timestamp>.<custom_name>.<ext>` (e.g. `20260512_090120.客户访谈.wav`). The legacy single-`.md` file (no `.meeting`/`.interview`/`.sharing` infix) is still recognised for read / open / delete.

Suffix routing lives in `_NOTES_SUFFIX` (`meeting` → `.meeting.md`, `interview` → `.interview.md`, `sharing` → `.sharing.md`); `MODES = tuple(_NOTES_SUFFIX.keys())` is the single source of truth driving argparse `choices=`, the mode→label dict in `generate_notes`, and the GUI scanner.

## Common Edit Patterns

**Add a new LLM provider**: add entry to `DEFAULT_CONFIG["llm"]`, add a `_llm_<name>()` function, dispatch in `_llm_run()`.

**Add a new STT provider**: add entry to `DEFAULT_CONFIG["stt"]`, add `_transcribe_<name>()`, dispatch in `transcribe()`.

**Change prompts**: edit `cfg["prompts"]` in `config.jsonc` (the user-facing surface, accepts both `str` and `list[str]`). The built-in defaults live in `_PROMPT_DEFAULTS` (above `DEFAULT_CONFIG`) but per the [Project Rules](#project-rules) section, `_PROMPT_DEFAULTS` is fallback only — every prompt also ships as an editable block in `config.jsonc`, and the two must stay byte-identical. Keys: `polish` is at the top level (mode-agnostic); `notes_zh` / `notes_en` live under `meeting`, `interview`, and `sharing` respectively. All call sites read via `_resolve_prompt(cfg, key, mode=None)`.

To customise just one mode without copy-pasting every default, drop the override into `config.jsonc` — `_deep_merge` keeps the other keys defaulted. For example, to ask the sharing-summary prompt to emphasise code snippets:

```jsonc
{
  "prompts": {
    "sharing": {
      // The literal "{transcript}" token is substituted via str.replace,
      // so other braces in your prompt do NOT need to be escaped.
      "notes_zh": [
        "你是一位技术分享整理助手。请在保留原有结构（分享概览 / 分享正文 / 核心要点 / 最佳实践 / 关键洞察 / 适用边界 / 风险与权衡 / 问答 / 行动建议）的基础上：",
        "- 在「分享正文」中**逐字保留代码片段、命令行、链接**，并用 ``` 围栏标注语言；",
        "- 「最佳实践」按「Do / Don't」两列罗列；",
        "- 「问答」若某问主讲人未直接回答，标注「（未直接回答 / 待跟进）」。",
        "",
        "---",
        "【分享转写】",
        "{transcript}"
      ]
    }
  }
}
```

The `notes_en` side falls back to the default — partial overrides are fine. Both `str` (literal) and `list[str]` (joined on `\n`) are accepted at every prompt slot.

**Modify GUI layout**: widgets live inside `cmd_ui()`'s three interface classes — `RecordingInterface`, `HistoryInterface`, `ConfigInterface` — all wrapped in `MainWindow`. Card surfaces via `_style_as_card(widget, padding=N, name="...")`. Pipeline-button styling via `_apply_open_btn_style(btn, is_open=bool)`.

**Add a translation key**: insert the key into both `_LABELS["zh"]` and `_LABELS["en"]` (top of `cmd_ui()`). Read in widgets via `_t("namespace.key")` or `self._i18n(widget, "namespace.key")` for the static-label callback variant.
